Documentation / Integration

Ploinky integration and evaluation

ALA operates as a standalone CLI and may also run as a Ploinky agent. Both forms preserve the same caller-owned mount contract and result separation.

Caller-owned mounts

ALA mounts only the directories the caller supplies. The caller owns task-skill discovery and preparation. --cwd <path> [as <alias>] is the writable working directory, mounted at its canonical absolute path, or under /workspace/<alias> when an alias is given; the coding agent runs there. Each --folder <path> [write] [as <alias>|at <absolute-path>] [expose] is read-only unless marked write and is mounted the same way. A read-only ancestor may contain the writable cwd; ancestors are mounted before descendants. When --cwd is omitted ALA creates and retains a private temporary directory. See DS004 for the complete mount and session contract.

An embedding host can prepare its own dependencies and configuration, then pass --folder /absolute/runtime as runtime. ALA mounts the folder read-only at /workspace/runtime. Omit the alias to keep the original absolute destination. A Unix socket inside a read-only mount remains usable for communication if its permissions allow access. The host owns the socket protocol, authentication, acknowledgements and cleanup. ALA neither reads configuration files nor starts an integration server.

Deployment and configuration

Callers may use --folder <source> at <absolute-destination> expose for an explicit read-only export. The destination must be normalized, must not conflict with reserved paths or duplicate another mount, and may overlap a folder ancestor only when that ancestor is read-only. If --ignore masks the source's parent, only a strict subdirectory may be exported to a destination outside the mask; the parent, ordinary aliases and other private data remain hidden. ALA treats these as generic directory binds and never discovers or interprets caller task skills.

The npm package exposes the ala executable and declares AchillesAgentLib as the Git dependency ploinky-agent-lib in package.json. User configuration resolves from an explicit --config <file> first; otherwise ALA treats ALA_CONFIG_PATH as a root directory, falls back to $HOME, and uses the root's .ala/config.json. The file accepts only codingAgent, the default backend; models, one native model identifier per backend; and efforts, one native effort per backend with a configured model. Any other field fails with exit code 2, so an older file with version or codingAgents must be rewritten by hand. The file never holds agent credentials or provider configuration.

ALA reuses AchillesAgentLib model configuration and tags when present. CLI model, tag, reasoning-effort, model-configuration, and dependency-path overrides take precedence over their environment equivalents.

Local coding-agent installation and configuration remain owned by each agent CLI. ALA detects executable paths through CODEX_BIN, OPENCODE_BIN, PI_BIN, CLAUDE_BIN, standard installation paths, and PATH, resolves launchers to their existing interpreter or package prefixes, and mounts those runtime trees read-only without copying or reinstalling them. A prefix below the mounted working directory appears under /run/ala-agent-runtime, with the executable and runtime PATH translated to that location. The prefix basename is preserved so local node_modules dependency lookup still works. Other prefixes retain their existing paths, including absolute interpreter and helper references. This mapping leaves the working directory, controlled home, and native continuation unchanged. The ALA configuration stores the default backend and explicit native model and effort selections; it never stores folder registrations or authentication credentials. Coding-agent deployments require Linux Bubblewrap. ALA clears the inherited task environment, mounts only known authentication/state directories read-write in an isolated home, and never falls back to an unsandboxed backend process.

When hosted by Ploinky, the same operations may be exposed through its CLI, router, and WebChat. Coding-agent execution still requires a detected Codex, OpenCode, Pi, or Claude Code backend. Standalone operation must not depend on Ploinky.

An embedding process may set ALA_EVENT_STREAM=1 to receive newline-delimited structured progress records on standard error while standard output remains reserved for the normalized final result. The records expose AchillesAgentLib tool name and reason plus visible coding-agent messages; they do not expose hidden reasoning. This transport is opt-in so ordinary non-interactive diagnostics remain unchanged.

An embedding application that needs conversation history runs coding-agent turns with --session-id. ALA then writes a session transcript under $ALA_SESSIONS/sessions/, or <cwd>/.ala/sessions/ when the variable is unset. Point ALA_SESSIONS at the application's own state directory to keep transcripts out of the mounted workspace. Pass --turn-id to correlate records with the application's own turn identifiers. When the prompt sent to the agent wraps the user's words in extra instructions, start ALA with --control-stdin and no --task or --taskFile, then write {"type":"prompt","prompt":"...","displayText":"..."} as the first stdin line. The agent receives prompt and the transcript shows displayText, the text the user typed, and the application needs no prompt file. ALA emits session-ready before the prompt arrives and starts the coding agent only after it. Follow-up messages sent through control stdin can carry a displayText for the same reason. The application reads transcripts only through the advanced-language-agent/transcript package export, using listSessions, readSession, readTurn, and their synchronous variants, so it never depends on the line format. ALA keeps the files; the application decides when to delete a session.

Hosts that present native permission prompts must attach --control-stdin and select --permissions ask-for-approval. Display each coding-agent-request using its advertised options, send a correlated interaction-response immediately, and dismiss it on coding-agent-request-resolved. Keep approval messages out of conversation history and never translate a native request into a host-maintained authorization cache. The command reference defines the complete event and response contract. Claude Code offers Allow once and Deny for each can_use_tool request. Pi rejects ask mode; a missing reply channel declines the operation rather than granting access.

Provision compatible native executables and authentication before launching tasks. Codex app-server approvals are based on the verified 0.139.0 protocol; OpenCode execution verifies the unprefixed session/permission API evidenced by v1.15.10; Pi RPC requires 0.85.1 or a verified compatible release, with the package's supported Node.js version; Claude Code requires 2.1.0 or newer. Log Claude Code in with claude under the same configuration directory ALA will mount, <home>/.claude for an explicit --home, or supply ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_BASE_URL, or CLAUDE_CODE_OAUTH_TOKEN. Claude Code accepts only Anthropic credentials. Its adapter uses the initialize, can_use_tool, and interrupt control requests that the Claude Agent SDK exchanges with the CLI, so a Claude Code release that changes that protocol also breaks ALA. Native session grants are backend-owned and need not persist across a newly owned process. OpenCode's per-execution server binds loopback, uses a fresh private password, and is stopped on cancellation or event-stream failure. Do not expose that control server as a public Ploinky endpoint.

Distribution-owned contracts

The standalone distribution defines exit code 0 for success, 2 for usage or configuration errors, 3 for input and output errors, 4 for repository resolution errors, 5 for execution and sandbox errors, and 130 for interruption. Remote-agent protocols, retained task-workspace values, and retry limits remain deployment contracts governed by the design specifications.
