Documentation / Integration

Ploinky integration and routing evaluation

ALA operates as a standalone CLI and may also run as a Ploinky agent. Both forms preserve the same task-selection and result-separation contracts.

Skill manifests and mounts

An embedding host such as RoboTeam chooses the skills before starting ALA. The --skill-catalog <path> option accepts either a JSON manifest file or a canonical catalog directory. For the manifest format, the host writes skill-catalog.json as an array of absolute paths visible to the ALA process. Each entry points directly to one self-contained skill directory with a valid Anthropic SKILL.md:

[
  "/data/robots/robot-id/skillsets/generation/read-pdf",
  "/data/robots/robot-id/skillsets/generation/write-doc"
]
ala --home /data/robots/robot-id/home --cwd /workspace/project --ca codex \
  --skill-catalog /data/robots/robot-id/runtime/tasks/task-id/skill-catalog.json \
  --task "Review the report"

ALA reads the array, resolves canonical paths and deduplicates identical targets. It validates each descriptor's name and description, rejects nested descriptors and duplicate or reserved names, and builds the same per-skill read-only mounts used by ordinary repository discovery. The directory basename does not select the mount name; the descriptor's name does.

The coding agent receives the selected names, descriptions and descriptor paths, then reads the relevant SKILL.md and its local resources. ALA does not copy the directories, expose the entire repository, mount the manifest into the workspace or interpret skillsets.md. The sandbox overlays .agents/skills so unselected workspace skills are hidden there, leaving host files unchanged. Other files already authorized through cwd or home retain their existing access.

The manifest replaces configured and environment-provided repositories for this invocation. [] selects no task skills, and interactive repository mutations are disabled. ALA reports malformed JSON, missing skill paths and invalid descriptors with repository exit code 4. It never edits the caller-owned manifest. RoboTeam removes deleted skill paths before invoking ALA on a new execution or continuation; the same manifest can therefore contain fewer entries on resume. Native conversation metadata remains independent of the skill manifest.

For a directory catalog, pass its canonical absolute path instead of the JSON file. It may be empty and may contain .catalog.json with {version:1,revision,policyVersion,entries:[{identity,name}],diagnostics:[]}. Versioned catalogs require exactly one immediate <name>/SKILL.md for every entry; missing, extra or nested descriptors and malformed metadata fail visibly. ALA retains recursive discovery for metadata-free directory catalogs. Directory catalogs and JSON manifests both convey an authoritative current revision on every execution, including an empty selection, and require the native agent to reread current descriptors and resources. JSON revisions derive from selected canonical paths, file contents, executable modes and symlink text; legacy directory revisions derive from content and modes. See execution options for native registration checks and the continuation contract.

Deployment and configuration

The npm package exposes the ala executable and declares AchillesAgentLib as the Git dependency ploinky-agent-lib in package.json. User configuration resolves from an explicit --config <file> first; otherwise ALA treats ALA_CONFIG_PATH as a root directory, falls back to $HOME, and uses the root's .ala/config.json. Its version-1 codingAgents.models object may persist one native model identifier for each supported backend without storing agent credentials or provider configuration. ala repo add, ala repo remove, and ala repo list manage persistent task repositories; add accepts only a Git URL and creates a managed clone under the ALA data directory, while ALA_TASK_REPOSITORIES supplies platform-delimited local repository paths through the environment.

ALA reuses AchillesAgentLib model configuration and tags when present. CLI model, tag, reasoning-effort, model-configuration, and dependency-path overrides take precedence over their environment equivalents. Task-repository configuration remains independent from the ALA installation so a deployment can install only the task families it needs.

Local coding-agent installation and configuration remain owned by each agent CLI. ALA detects executable paths through CODEX_BIN, OPENCODE_BIN, PI_BIN, standard installation paths, and PATH, resolves launchers to their existing interpreter or package prefixes, and mounts those runtime trees read-only without copying or reinstalling them. A prefix below /workspace appears under /run/ala-agent-runtime, with the executable and runtime PATH translated to that location. The prefix basename is preserved so local node_modules dependency lookup still works. Other prefixes retain their existing paths, including absolute interpreter and helper references. This mapping leaves the task cwd, controlled home, and native continuation unchanged. The ALA configuration stores backend priority, explicit native model selections, and web-search state; it never stores folder registrations or authentication credentials. Coding-agent deployments require Linux Bubblewrap. ALA clears the inherited task environment, mounts only known authentication/state directories read-write in an isolated home, and never falls back to an unsandboxed backend process.

When hosted by Ploinky, the same operations may be exposed through its CLI, router, and WebChat. Anthropic task-skill execution still requires a detected Codex, OpenCode, or Pi backend. Standalone operation must not depend on Ploinky.

An embedding process may set ALA_EVENT_STREAM=1 to receive newline-delimited structured progress records on standard error while standard output remains reserved for the normalized final result. The records expose AchillesAgentLib tool name and reason plus visible coding-agent messages; they do not expose hidden reasoning. This transport is opt-in so ordinary non-interactive diagnostics remain unchanged.

Hosts that present native permission prompts must attach --control-stdin and select --permissions ask-for-approval. Display each coding-agent-request using its advertised options, send a correlated interaction-response immediately, and dismiss it on coding-agent-request-resolved. Keep approval messages out of conversation history and never translate a native request into a host-maintained authorization cache. The command reference defines the complete event and response contract. Pi rejects ask mode; a missing reply channel declines the operation rather than granting access.

Provision compatible native executables and authentication before launching tasks. Codex app-server approvals are based on the verified 0.139.0 protocol; OpenCode execution verifies the unprefixed session/permission API evidenced by v1.15.10; Pi RPC requires 0.85.1 or a verified compatible release, with the package's supported Node.js version. Native session grants are backend-owned and need not persist across a newly owned process. OpenCode's per-execution server binds loopback, uses a fresh private password, and is stopped on cancellation or event-stream failure. Do not expose that control server as a public Ploinky endpoint.

AchillesCLI invokes ALA with --ploinky-task <directory>. ALA mounts the SDK, routing descriptors and private context.json read-only. This explicitly grants the native agent the caller's Ploinky identity. Each launch skill imports /Agent/client/AgentMcpClient.mjs and calls MCP directly. The writable /run/ploinky-task/events directory carries one-way task notifications to the host for chat observation, never MCP requests. ALA starts no socket or proxy. The host drains notifications and removes the private context after its child exits. The selected-skill overlay hides unselected descriptors without modifying host files.

The legacy --runtime-bridge option remains available for other embedding hosts. AchillesCLI does not use it. Neither integration is exposed by default.

Routing evaluation

Routing evaluation compares explicit Anthropic skill selection, coding-agent catalog selection, and symbolic routing before catalog fallback. The shared corpus covers canonical instructions, paraphrases, multilingual requests, spelling errors, ambiguous and multi-step requests, missing parameters, and unsupported work.

Symbolic measurements include correct and incorrect direct decisions, abstention, fallback, and final correctness after fallback. A false confident decision receives a greater penalty than abstention because it bypasses the safe default route with the wrong method.

Distribution-owned contracts

The standalone distribution defines exit code 0 for success, 2 for usage or configuration errors, 3 for input and output errors, 4 for repository or task-skill errors, 5 for execution and sandbox errors, and 130 for interruption. Remote-agent protocols, task-workspace retention, retry limits, and symbolic-routing thresholds remain deployment contracts governed by the design specifications.
