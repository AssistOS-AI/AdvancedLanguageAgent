Advanced Language Agent Documentation

Advanced Language Agent (ALA) is a system-installed CLI for language and documentation tasks. A human or agent submits an instruction and optional input; the CLI runs the request on a detected coding agent and returns the requested result in one-shot mode or across an explicitly interactive process.

ALA mounts exactly the directories the caller supplies through --cwd and --folder. It does not discover or prepare task skills or infer their mounts; callers own their directory layout and any task methodology.

From instruction to result

A request may carry input through command arguments, standard input, a URL, or a file. Every execution runs on the coding agent chosen by execution routing: the backend named with --ca/--agent, or with the default auto a session's saved backend, the configured default, or the first available one. ALA runs the request on that backend inside its sandbox against the caller's mounted directories, and fails with exit code 5 when no coding agent is available. The runtime writes the requested result to standard output or a file, while diagnostics use a separate channel.

A one-shot command creates a new runtime. Reusing --cwd alone does not resume a conversation. Explicit --session-id and --resume-session restore the same native conversation and pinned coding backend across processes, and ALA records that conversation in an append-only session transcript. An interactive command retains these in memory until exit. A caller-supplied cwd is never deleted by ALA, and ALA retains the temporary directory it creates when --cwd is omitted. See persistent session commands for continuation and live input.

CLI and user configuration

The executable is ala. The JSON configuration uses $HOME/.ala/config.json. ALA_CONFIG_PATH selects another root directory and moves the configuration file below its .ala/ child, while --config <file> has the highest priority for one command. It holds only the default backend in codingAgent and per-backend models and efforts; ALA rejects any other field.

Payloads use --text, --file, --url, or --stdin, and --output writes the clean result to a protected file. Directories are supplied with --cwd <path> [as <alias>] and repeatable --folder <path> [write] [as <alias>|at <absolute-path>] [expose]. Repeatable --ignore /absolute/directory masks private directories with empty read-only mounts. The command reference documents every command and option.

ala agent list reports the names of detected Codex, OpenCode, Pi, and Claude Code backends in that fixed order, ala agent models <name> --json reports one backend's models with the efforts each supports, and ala status (or /status in a session) shows which backends are installed, which hold a login, and which one --ca auto would use, without running any of them. In an interactive session, /agent use <name> saves the default backend, /agent <name> models lists a backend's available model identifiers, /agent <name> model <model-name> persists its selection, /agent <name> model default removes the override, and /agent <name> effort <effort|default> sets or removes the effort of that model. --agent auto, the default, selects a session's saved backend, then the configured default backend when installed, otherwise the first available of Codex, OpenCode, Pi, Claude Code, while --agent codex, --agent opencode, --agent pi, or --agent claude selects one backend explicitly. Every backend and model-list process runs through Linux Bubblewrap; ALA mounts the already installed backend runtime read-only, never installs a task-local copy, and never falls back to unsandboxed execution. Interactive coding-agent output replaces the waiting indicator as soon as a supported event arrives, while the normalized final answer remains on standard output. Codex and OpenCode always run with web search enabled, and Claude Code keeps its built-in WebSearch and WebFetch tools on. Pi has none, and ALA does not add a third-party search extension.

Every native process starts through an execution provider: the Bubblewrap provider is the standalone default, and an embedding service that confines processes itself selects the protocol provider with --execution-provider protocol. In that embedded mode ALA builds no sandbox, uses virtual paths, and fails with exit code 5 rather than starting a process itself or falling back to Bubblewrap; see the execution and command pages.

Embedding orchestrators may supply --home, --cwd, --folder, --task or --taskFile, --MCPServers, and --ca. The explicit home contains coding-agent configuration, the explicit cwd remains persistent, each mounted directory stays at its canonical path or alias, and MCP URL overrides are transient.

Product and repository boundaries

Explicit folder destinations use at /absolute/destination. The optional expose modifier authorizes a read-only subtree export to a separate destination, including a strict subdirectory of an ignored source. Ordinary ignored aliases remain masked, writable exports and duplicate destinations are rejected, and ALA never chooses what to export. See caller-owned mounts.

ALA is generic execution infrastructure. It does not implement or distribute task-specific SKILL.md definitions and does not require any catalog. A caller that owns task methods installs them in its own working directory and references them in its own prompt; ALA simply runs the selected backend with the directories it was given.

Imported task skills and their design specifications stay in their owning repositories. The core documentation describes how callers integrate with the runtime without copying skill-specific documentation.

Runtime defaults and verification

Every execution uses a coding agent; ALA calls no model provider directly and has no runtime npm dependencies. An explicit --ca always uses the chosen backend and fails when it is not available.

Coding style, source layout, file-size limits, and modular test organization are defined by DS001. Tests are grouped by concern and independently cover argument parsing, input handling, configuration persistence and precedence, coding-agent delegation, mount layout, output separation, and result-file protection.
