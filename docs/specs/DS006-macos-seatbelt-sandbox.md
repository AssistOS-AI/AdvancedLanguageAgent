## Introduction

[ALA](index.html) confines every coding-agent process and every native model-catalog process in a [sandbox backend](wiki.html#definition-sandbox-backend): Bubblewrap on Linux, which DS002 and DS004 define, and Seatbelt on macOS, which this specification defines. The macOS backend runs each process under a deny-by-default profile applied by `/usr/bin/sandbox-exec`. Seatbelt follows paths where Bubblewrap builds a mount namespace, so it gives weaker guarantees in the places the guarantee table names.

## Core Content

### Backend selection and fail-closed behavior

ALA selects the backend from the platform of the running process, in `src/coding-agents/sandbox-backend.mjs`: `linux` selects Bubblewrap and `darwin` selects Seatbelt. No environment variable and no option selects or disables a backend. `ALA_BWRAP` names a Bubblewrap binary and has no effect on macOS, where the launcher is the fixed path `/usr/bin/sandbox-exec` with no override, because a replaced launcher could run agents unconfined. On any other platform ALA fails with exit code `5` and `Coding-agent execution requires Linux (Bubblewrap) or macOS (Seatbelt); no unsandboxed fallback is permitted.` before any agent starts. The Bubblewrap implementation in `src/coding-agents/sandbox.mjs` is unchanged, and the Linux launch uses exactly the inputs it used before the second backend existed.

The macOS backend reports the capabilities `privateProc` as satisfied, because macOS has no procfs to isolate, and `bindDescriptors` as unavailable, because Seatbelt rules name paths and cannot bind a descriptor. ALA never starts a coding agent or a model-catalog process on macOS without the profile. Each failure in the following table happens before the agent starts and exits with code `5`, except the changed directory, which exits with code `78`.

| Condition | Message |
| --- | --- |
| An adapter starts a process without a sandbox description | `Coding-agent processes must run inside the ALA Seatbelt sandbox.` |
| `/usr/bin/sandbox-exec` is missing or not executable | `Coding-agent execution on macOS requires /usr/bin/sandbox-exec (Seatbelt); no unsandboxed fallback is permitted.` |
| The start probe reads another process's environment | `The macOS Seatbelt sandbox does not hide other processes' environments on this system; no unsandboxed fallback is permitted.` |
| The start probe fails for any other reason, `/usr/bin/perl` missing included, or ALA already runs inside another macOS sandbox | `The macOS Seatbelt sandbox could not start (<diagnostic>). ALA may already be running inside another macOS sandbox, which cannot be nested; no unsandboxed fallback is permitted.` The diagnostic is the last 512 characters of the probe's error or output with runs of whitespace collapsed. |
| `--expect-dir` names a directory whose recorded identity matches | `--expect-dir requires descriptor binds, which the macOS Seatbelt sandbox cannot provide.` |
| `--cwd ... as <alias>`, `--folder ... as <alias>`, `--folder ... at <path>` or `expose` is requested | `--cwd as <alias>, --folder as <alias>, --folder at <path> and expose need a mount namespace and are not supported on macOS.` |
| A profile parameter is not an absolute, normalized, real path | `Seatbelt profile parameter <NAME> must be an absolute, normalized, real path: "<value>"` |
| The workspace or the agent executable no longer resolves | `Coding-agent sandbox workspace or executable is unavailable.` |
| A mounted folder equals the working directory | `A mounted folder duplicates the working directory.` |
| `--home` no longer resolves | `Coding-agent home is unavailable.` |
| A granted directory changed or disappeared | `A granted directory changed or is unavailable: <source>` with exit code `78` |

### Start probe

Before each spawn ALA verifies that the profile hides other processes' environments, and a successful result is reused for 30 seconds as described below. The probe runs `/usr/bin/sandbox-exec` with the constant base rules of the profile and the system read roots, working directory `/` and `PATH=/usr/bin:/bin`, and starts a module-free `/usr/bin/perl` reader that calls `sysctl` for `kern.procargs2`. The reader reads `kern.procargs2` for ALA's process ID and for its own, and the probe passes only when the first read is refused and the second succeeds. The second read is the positive control that proves the reader ran. A refused second read, a missing perl, a timeout of five seconds or any other output fails the attempt, and the probe makes two attempts. Any other outcome refuses every agent with the messages above; a readable first read selects the environment message.

A successful probe is cached for 30 seconds, keyed by the launcher and the complete probe arguments, which include the profile text. A failure is remembered with its diagnostic. The probe exists because the behavior it checks is a combination of two rules whose interplay Apple does not document, and a macOS update can change it.

### Profile

`src/coding-agents/seatbelt-profile.mjs` turns the grants of one launch into profile text and parameters. The profile starts with `(version 1)` and `(deny default)`. Seatbelt evaluates rules in order and the last matching rule wins, so the order of the rules is part of the boundary: base rules, read-only system roots, the supervisor read rule, parent metadata, home, temporary folder, mounts, state roots and runtime roots in ascending path length, masks, root guards, link guards, and rename guards. An ancestor therefore never overrides a descendant. A state root below a read-only mount stays writable, and a read-only folder or an agent installation below a writable root stays read-only.

No path is written into profile text. Every path is passed as a `-D NAME=value` parameter and referenced with `(param "NAME")`, so no path can inject a rule. Each value must be absolute, normalized, free of NUL and, when ALA resolves it, equal to its real path; otherwise the launch fails with exit code `5`. `tests/fixtures/seatbelt-profile.sb` and `tests/fixtures/seatbelt-profile.params.json` pin the profile for a fixed input.

Process and signal rules allow `process-fork` and `signal` to targets in the same sandbox only. The profile then denies `process-info*` explicitly and allows `process-info*` for the same sandbox, and it allows `sysctl-read` and denies `sysctl-read` for every name that matches `^kern\.proc`. Both rule pairs are required. The sysctl deny hides the process list; process IDs in use remain observable through signal `0`. The explicit `process-info*` deny followed by the same-sandbox allow is required even under `(deny default)`. Either pair alone leaves the arguments and environment of an outside process of the same user readable through `kern.procargs2`, and only the combination refuses that read while the process's own arguments stay readable. The start probe and `tests/seatbelt.test.mjs` check this combination, and the test removes the deny rule of each pair in turn and expects the environment refusal. An Apple system binary's environment is not returned even without a sandbox, so a check needs a non-Apple target whose marker is first confirmed outside.

Network rules allow outbound IP connections to any remote address, and inbound and bind for local IP addresses. Outbound unix-socket connections are allowed only to `/private/var/run/mDNSResponder` and below the home, the temporary folder, every mount and every state root. A runtime root grants none, and a mask denies it. Binding a unix socket is not allowed. The only Mach service a process may look up is `com.apple.system.opendirectoryd.libinfo`.

Devices are limited to read and write on `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/tty`, `/dev/dtracehelper` and `/dev/ptmx` with `pseudo-tty`. The profile denies every `/dev/ttys*` path and then allows it only together with the `com.apple.sandbox.pty` extension filter, so a process can open the terminal it allocated inside the sandbox and is refused another session's terminal. The profile grants read of `/` and metadata of `/etc`, `/tmp` and `/var`, and metadata of every parent folder of an allowed root.

Read roots are the real paths of these folders, kept only where they exist, with nested roots collapsed into the outermost: `/usr/bin`, `/usr/lib`, `/usr/libexec`, `/usr/sbin`, `/usr/share`, `/bin`, `/sbin`, `/System`, `/private/etc`, `/private/var/select`, `/private/var/db/timezone`, `/Library/Frameworks/Python.framework`, the developer directory that `/private/var/db/xcode_select_link` resolves to, and for each of `/opt/homebrew` and `/usr/local` that exists, the folders `Cellar`, `opt`, `bin`, `sbin`, `lib`, `libexec`, `share`, `include`, `Frameworks`, `etc/openssl@3` and `etc/ca-certificates`. A whole prefix `etc` or `var` is never a root, because they hold other programs' configuration and state. Homebrew's Node links libraries from other kegs and needs `etc/openssl@3`, so a single keg is not enough. `/private/etc` is readable in full. `/System` is readable, and the `/System/Volumes/Data` path of a folder outside the grants is still refused. A program runs only from a readable root: the profile has no general `process-exec*` rule, and each read root, home, temporary folder, mount and state root grants `process-exec*` together with read, so a binary in a hidden folder cannot be started either.

The mounts are the working directory, writable, and each `--folder`, read-only unless marked `write`. A read-only mount allows read and execution and denies write. A writable mount allows read, write and execution. Without `--home`, the agent's state folders are writable roots. The private temporary folder and either the explicit `--home` or the private home are writable roots as well. Runtime roots are the folders that `collectAgentRuntimeMounts` returns for the agent executable and for the Node executable that runs the supervisor, minus any root inside or containing a software prefix, because an npm-global agent would otherwise expose a whole prefix. A runtime root is read-only and has no socket grant. A runtime root that lies inside a writable root, for example a standalone agent's release folder inside its own state folder, stays read-only. A runtime root that is itself a writable root keeps its write access.

Masks come from `--ignore`. After every allow, each mask denies read, write, execution and outbound unix-socket connections to its target, as a subtree for a directory and as a literal for a file. A masked path answers with `EPERM` to read, list and stat, and upper-case, lower-case and Unicode-normalized variants of the path are denied as well.

Root guards deny `file-write-unlink` on the literal path of every granted root: the working directory, every folder, the state roots, the home, the temporary folder and the runtime roots. A `(subpath ROOT)` rule also matches `ROOT` itself, so without these guards a confined process could rename, swap, remove or replace by a link the root of a writable grant and move its rules elsewhere. Link guards protect the symbolic links on the way from the agent's program to its real file, when a link lies inside a writable root: a standalone Codex install, for example, selects its program through a `current` link inside the writable `~/.codex`, and a confined run that could retarget it would choose the program a later unconfined run starts. ALA finds these links from the executable path it was given, from the binary override variable, from the standard installation paths, and from every `PATH` entry that resolves to the same program, and a link can then be neither replaced nor renamed onto. Links through which a user starts Node are not found or guarded. Rename guards deny `file-write-unlink` on every folder strictly between a writable root and any root, guarded link or mask nested in it, so renaming a parent cannot move a protected path out of reach. Creating files in those folders still works. The profile also grants read of the supervisor file, so the supervisor needs no other grant.

### Launch

For each process ALA starts `/usr/bin/sandbox-exec -p <profile> -D NAME=value ... <node> <ALA>/src/coding-agents/seatbelt-supervisor.mjs 3 <command> <args...>`, where `<command>` is the real path of the agent executable. `sandbox-exec` replaces itself with the supervisor, so the child's process ID leads a new session and process group. ALA spawns it detached, with the working directory the caller chose, with an environment that is exactly the re-rooted allowlist and not merged with ALA's own, and with the caller's three standard streams plus one pipe as descriptor `3`.

The environment is the backend's allowlist from DS002 with `HOME` set to the real path of the private home or of `--home`. Every value that equals the sandbox home, or starts with it followed by `/`, is re-rooted to that path. `USER` and `LOGNAME` equal the basename of the sandbox home, `ala` by default, the XDG folders lie below that home, `TMPDIR` is the private temporary folder, and `PATH` lists each runtime root's `bin` folder and the root itself, then each software prefix's `bin`, then `/usr/bin:/bin`.

Each service owns one base folder, created with `mkdtemp` under the real temporary directory and named `ala-seatbelt-<pid>-<random>`, with mode `0700`. Each process gets `p-<random>/tmp` and, without `--home`, `p-<random>/home` below it. With `--home`, the home is the explicit folder itself, nothing is bound at the sandbox home, and only the temporary folder is private. Without `--home` ALA creates, for each state folder of the backend, a symbolic link from the re-rooted path in the private home to the real state folder, which the profile allows read and write. The profile is the boundary and no guarantee depends on the links. A state folder that does not exist is not linked. The private folder of a process is removed when the process closes, and the base is removed when the service closes and when ALA exits.

Before every spawn ALA re-checks the granted directories, because a rule that names a path would follow a host process that swapped it. For the working directory and each `--folder` that the service opened, the real path must equal the recorded source and the device and inode must equal the identity recorded when it opened the directory. The working directory, an explicit `--home` and each state folder are recorded at their first spawn and re-checked at every later spawn of the same service. Any mismatch fails with exit code `78` and `A granted directory changed or is unavailable: <source>`. A state folder that was seen once and no longer exists also fails with `78`, so a state folder deleted on the host makes every later turn of that service exit `78` until ALA restarts. The check does not cover a later swap: until every confined process has ended, a host process that renames or replaces a granted directory or a folder above it redirects that directory's rule to whatever then lies at the path.

The supervisor runs inside the sandbox as the leader of the process group. It starts the command with the standard streams and without descriptor `3`, ignores `SIGTERM`, `SIGINT` and `SIGHUP` itself, because a group signal from ALA reaches the command directly, and reports how the command ended. When descriptor `3` ends, closes or fails, which happens when ALA dies even through `SIGKILL`, the supervisor sends `SIGKILL` to its whole process group at once. The test allows five seconds. The supervisor exits with the command's exit code and re-raises a command's signal on itself. For `SIGPIPE`, `SIGXFSZ` and `SIGUSR1`, which Node ignores or handles, it exits with 128 plus the signal number. When the command cannot start it prints one line, `ALA Seatbelt supervisor could not start <command>: <code or message>`, and exits `127` for `ENOENT` and `126` for any other error. Wrong arguments exit `64`.

ALA replaces the child's `kill` with a signal to the process group. After `SIGTERM`, `SIGINT` or `SIGHUP`, ALA sends `SIGKILL` to the group 2000 milliseconds later unless the child has already exited, because the command may ignore the signal while the supervisor waits for it. Signal `0` and other signals are only sent. When the child exits, ALA sends `SIGKILL` to the group once, so descendants that stayed in the group end with it, and `kill` is a no-op afterwards because the group identifier may be reused.

### Cleanup

Removal of a private folder never throws, because it runs in child-process listeners and at exit, where an exception would crash ALA and lose the result of the turn. ALA's own process never walks the content of a private folder, because a descendant that left the process group may keep swapping folders for links while the cleanup runs. The removal runs in a helper confined by its own Seatbelt profile, whose only writable root is the folder being removed and which may execute only `/bin/rm`, `/bin/chmod` and `/usr/bin/chflags`, so the kernel refuses any effect outside that folder whatever the paths resolve to at that moment. The helper runs `rm -rf` with a ten second limit. When the folder remains, ALA repairs it through the helper with `chflags -R -P nouchg,nouappnd`, then `chmod -R -P u+rwx`, then `chflags` again, each with a five second limit, and removes it once more. If the folder still remains after that, or the helper cannot run, the folder is left and reported once as `ALA could not remove the Seatbelt private folder <folder>; a later run tries again.`, as a process warning, or as a line on standard error when ALA is exiting. There is no unconfined fallback.

ALA killed by `SIGKILL` cannot remove its folders. When a service creates its base folder, ALA removes folders named `ala-seatbelt-<pid>-<random>` directly in the temporary root whose owner process is no longer running, only when they are real directories owned by the current user, and only through the confined helper.

### Options refused on macOS

Seatbelt shows every directory at its own path, so the features that need a mount namespace fail closed with exit code `5` before any agent starts. `--cwd <path> as <alias>`, `--folder <path> as <alias>`, `--folder <path> at <absolute-path>` and `expose` are refused with the mount message of the table above, and a launch that still receives such a mount refuses it as well. `--expect-dir` needs a descriptor bind. The command line checks the recorded identity of every `--expect-dir` first, on both platforms, so a link, a missing directory, a non-directory or another identity exits `78` before ALA reads its configuration, and a name that matches no `--cwd` or `--folder` is a usage error with exit code `2`. Only an identity that matches reaches the refusal with exit code `5`. Without `--expect-dir`, the identity re-check before every spawn is the only protection against a changed path.

### Guarantees compared

The table lists each Bubblewrap guarantee, what Seatbelt provides instead, and the residual difference.

| Bubblewrap guarantee | macOS equivalent | Residual difference |
| --- | --- | --- |
| The environment is cleared and the allowlist restored | The process is spawned with exactly the allowlist environment, re-rooted to the real home | Other processes' environments are unreadable only because of the rule pairs above, whose interplay is undocumented. The start probe refuses to run agents when the read succeeds. |
| The system is read-only through `--ro-bind` and `--remount-ro /` | A deny-by-default profile with a read allowlist of system and software roots | There is no remount, and writes fail with `EPERM`. Of each Homebrew prefix (`/opt/homebrew`, `/usr/local`) only the curated folders are exposed: its `etc` only through `etc/openssl@3` and `etc/ca-certificates`, and its `var` not at all, where Linux exposes all of `/usr` and `/etc`. `/private/etc` is exposed in full. |
| A private `/tmp` on tmpfs | A private temporary folder as `TMPDIR`; `/tmp`, `/private/tmp` and `/private/var/folders` are not granted | A program that hardcodes `/tmp` fails with `EPERM` where Linux gives it a private tmpfs. |
| The home is `/home/ala`, or `--home` bound there | `HOME` is the real path of a private folder, or of `--home` itself | The host path, including the user name, is visible. `USER` and `LOGNAME` stay `ala` by default. |
| The agent's state is bound into the home | Symbolic links in the private home point to the real state folders, which the profile allows read and write | The real paths are visible. On both platforms, without `--home`, the state folder is writable, so a confined run can change what the unconfined agent later reads from it. See the state folder residual below. |
| A stored login is visible through the state bind | File and environment logins only | No Keychain access. Claude Code needs a credentials file under its configuration directory, or a token variable. |
| Runtime and `PATH` come from the resolved prefix | A read allowlist of the agent's and Node's runtime roots and of curated Homebrew folders, with Homebrew `bin` on `PATH` | Wider than one prefix, because Homebrew Node needs libraries from other kegs. |
| The working directory is writable and folders read-only | Path rules in ascending order, last match wins | Path-based and not mount-based. |
| `--ignore` hides a path behind an empty mount or `/dev/null` | A deny rule after the allows | Read, list and stat answer `EPERM`. A rename guard protects the folders above a mask. |
| A path outside the mounts is absent (`ENOENT`) | A path outside the grants is unreadable | The existence of a hidden path is observable, for example through `existsSync`. Content, size and listings stay hidden. |
| Descriptors pin each directory (`--bind-fd`) | Identity re-check before every spawn | Rules follow paths for the whole life of every confined process, including a descendant that left the group. A host process that renames or replaces a granted directory, or any folder above it, at any time after the re-check redirects the rule to whatever then lies at that path; the re-check before each spawn detects only a change made before that spawn. `--expect-dir` is refused. The confined process cannot do this itself: it has no write access above a granted root, and the root guards and rename guards refuse renames of every root and of the folders between a writable root and a root nested in it. |
| A PID namespace and `--die-with-parent` | A new session and process group, a group kill on abort, on exit and when ALA dies, and a sysctl deny that hides the process list and other processes' details | Descendants that leave the group, for example through `setsid`, survive, still confined by the inherited profile. A confined process that stops the supervisor, which shares its sandbox, defeats the parent-death kill. Signals reach only processes of the same sandbox, and other processes' arguments and environments are refused by the rule pairs. Which process IDs are in use is observable: signal `0` to another process answers `EPERM` for a live one and `ESRCH` for a free one. |
| `--new-session` | `detached: true`, which starts a new session | None known. |
| A private `/proc` | Not applicable, and `privateProc` counts as satisfied | None. |
| IPC and UTS isolation | The only Mach lookup is the directory-service lookup, and the host name is not isolated | The host name is visible. |
| A private device tree | Read and write only for the fixed devices; a terminal only when it was allocated inside the sandbox | A path rule on `/dev/ttys*` alone would open another session's terminal. |
| No privilege through set-id programs | A set-id program cannot be executed | Agents cannot use programs such as `ps`. |
| No access to the user's service manager | launchd refuses job creation, variables and `launchctl kill`; the program choice is refused because it needs root | The launchd residual below. |
| The network is shared | IP sockets are allowed in and out, unix sockets only as stated above | Binding a unix socket is not allowed. |
| An agent's own nested sandbox | A nested `sandbox-exec` is refused with `sandbox_apply: Operation not permitted` | An agent that starts its own sandbox fails. Codex is told not to build one. |
| Aliases, `at`, `expose`, `/workspace` | Refused with exit code `5` | The features are absent on macOS. |

The launchd residual is not closed. A confined process can ask launchd to start, and to unload through `bootout` or `remove`, jobs that already exist in the user's login session. It cannot create a job, set a launchd variable, send a signal with `launchctl kill` or choose what program a job runs. It can still end a running job: `bootout` and `remove` stop the instance they unload, and `kickstart -k`, which the gate does not attempt, is documented to kill a running instance before restarting it. It cannot list jobs or read a job's definition, the disabled list or a launchd variable: `list`, `print`, `print-disabled` and `getenv` were refused on macOS 27.2.1, while `managerpid`, `manageruid` and `managername` still answer. The gate does not check reads. ALA adds no rule that only blocks the `launchctl` program, because a copy of it or another client would bypass that rule and suggest a boundary that does not exist. The gate does not attempt `launchctl disable`, unloading the whole login session or restarting real services, so whether a confined process can do those is not known. A caller that needs launchd excluded needs separation that ALA does not provide.

Further residuals follow from the rules and are not closed:

- Rules follow paths, not directories. Until every confined process has ended, a host process that renames or replaces a granted directory, or a folder above it, redirects that directory's rule to whatever then lies at the path, where Bubblewrap's descriptor bind pins the directory for the life of the sandbox. The re-check before each spawn detects only a change made before that spawn, so a caller must not move, replace or recreate a granted directory while a run is active.
- A confined process that stops the supervisor with a stop signal can keep running after ALA dies, because the parent-death kill is carried out by the supervisor. Its profile still applies.
- A descendant that leaves the process group survives the group kill, an abort and the exit of the child, and stays confined by the inherited profile.
- ALA reads no Keychain item. Claude Code on a Mac that stores its subscription login only in the Keychain cannot sign in inside the sandbox and needs a credentials file under its configuration directory or one of `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`.
- The agent's state folder is writable on both platforms without `--home`: on Linux through the bind at the sandbox home, on macOS through the state root. A confined run can therefore change what the unconfined agent later reads from it, for example its settings. Program-selection links are guarded on macOS only. A caller that needs this closed must pass a dedicated `--home`, whose content it prepares and treats as untrusted after a run.
- Neither the Rosetta runtime nor `/Applications` is a read root. ALA grants nothing there except the folder of an agent or Node executable that itself lies there. An agent that needs other files there cannot read them, and whether an agent that needs Rosetta starts is untested.
- Only the agent executable's own runtime root and Node's runtime root are added. A program outside every readable root (the system roots, the runtime roots, the home, the temporary folder, the mounts and the state roots), including a script interpreter named in a `#!` line, is not executable.
- An agent installed below Homebrew's `Caskroom` is not covered. A runtime root inside a software prefix is dropped in favor of the curated prefix folders, and `Caskroom` is not one of them.
- An agent that updates itself by rewriting or deleting its running release folder, or by retargeting a guarded program link such as Codex's `current`, fails inside, because that folder is a read-only runtime root and the link is guarded. Other files in its state folder stay writable, except that guarded links and the folders between the state folder and a runtime root or guarded link cannot be removed or renamed.
- `sandbox-exec` is deprecated and its profile language is undocumented, so a macOS update can change behavior. The pinned profile fixture, the live tests, the start probe and the gate below detect a change and do not prevent it.

### Escape gate

`scripts/seatbelt-escape-gate.mjs` is an opt-in check of the launchd residual under the profile ALA really builds. It runs only with `--run-launchd-attempts` and only on macOS, because it creates and removes real launchd jobs in the user's login session. It is not part of `npm test`. Run it after a change to the profile's allowlist or to the launch, and on every new macOS version.

The gate first proves with host-side controls that each refused request except `debug --program` works when it is not confined, and that each target job is in place before the attempts, so a job that never loaded cannot read as unloaded. It then runs the attempts from inside the profile through the coding-agent service, against throwaway jobs that it creates for the run. Every job, variable and marker carries a label unique to the run, and cleanup runs on success, on failure and on `SIGINT` or `SIGTERM`.

| Attempt from inside the profile | Required result |
| --- | --- |
| `submit`, `bootstrap` and `load` of a job | Refused |
| `setenv` of a launchd variable | Refused |
| `kill` of a running job | Refused |
| `debug --program` to run a chosen program through a job | Refused; launchd requires root for it whether or not the request is confined, so the refusal is not a sandbox control |
| `kickstart` of an existing job | Takes effect |
| `bootout` and `remove` of an existing job | Take effect |

The gate passes only when exactly the three accepted requests take effect, every other attempt is refused, all eight host controls worked, the positive marker shows that the sandboxed attempts ran, and no launchd job or variable of the run is left behind. A launchd request that stops taking effect also fails the gate, so that this specification is revisited. The exit code is `0` on a pass, `1` on a failure, `2` when the flag is missing or the platform is not macOS, and `130` or `143` after cleanup on `SIGINT` or `SIGTERM`. The permanent live test `tests/seatbelt.test.mjs` covers further escape attempts with host controls: a Keychain lookup, the SSH folder, the Keychain folders, a nested `sandbox-exec`, `open` and `osascript`.

### Test rules

`npm test` runs `scripts/run_tests.mjs`, which starts each test file with the Node test runner and removes every agent variable from the child environment first: each agent's binary override, state and home variables, allowed and credential variables, the four XDG folder variables, `ALA_CONFIG_PATH` and `ALA_SESSIONS`. The tests also clear these variables themselves, so that no test reaches an installed agent, an agent login or a real state folder, and `ALA_BWRAP` is kept because it selects the sandbox launcher and not an agent.

Tests are classified by backend. A test of Bubblewrap arguments, `ALA_BWRAP`, descriptor binds, aliases or tmpfs masks is Bubblewrap-only and keeps its own Linux condition. A backend-neutral live test runs wherever a sandbox can start. The pure profile tests run on every platform, and the live Seatbelt tests run on macOS only. A skipped sandbox test shows one of these fixed reasons.

| Reason | Where it appears |
| --- | --- |
| `Bubblewrap only (Linux): arguments, ALA_BWRAP, descriptor binds, aliases or tmpfs masks` | A Bubblewrap-only test on macOS |
| `Seatbelt is macOS-only` | A live Seatbelt test or a macOS refusal test on Linux |
| `macOS ps only` | The `ps` behavior test on Linux |
| `Coding-agent sandboxes exist only on Linux and macOS` | A backend-neutral live test on another platform |
| `Bubblewrap cannot start in this test process` or `Seatbelt cannot start in this test process` | A backend-neutral live test where the platform's sandbox cannot start; the Bubblewrap text also marks Bubblewrap-only Linux tests |
| `Bubblewrap unavailable` and `Requires a Bubblewrap with --bind-fd on Linux` | A Linux test whose Bubblewrap condition is not met |

Where ALA has a sandbox, a run in which none could start skips every live sandbox test and proves little. When the platform is Linux or macOS, `ALA_TESTS_WITHOUT_SANDBOX` is not `1` and the sandbox cannot start in the runner's process, `npm test` prints `FAIL: <Bubblewrap|Seatbelt> cannot start in this process, so every live sandbox test was skipped. Run the tests where a sandbox can start, or set ALA_TESTS_WITHOUT_SANDBOX=1 to accept this run.` and exits `1`. `ALA_TESTS_WITHOUT_SANDBOX=1` accepts such a run explicitly, for example inside a container without Bubblewrap.

The macOS tests are `tests/seatbelt-profile.test.mjs` for the pure profile, `tests/seatbelt.test.mjs` for confinement, `tests/seatbelt-roots.test.mjs` for root guards and link guards, `tests/seatbelt-lifecycle.test.mjs` for the supervisor, the cleanup and the sweep, `tests/seatbelt-cleanup.test.mjs` for removal racing a swap, `tests/sandbox-backend.test.mjs` for backend selection, the refusal texts and the unchanged Linux launch, `tests/sandbox-paths.test.mjs` for workspaces named through links, `tests/process-identity.test.mjs` for session-lock identity, and `tests/seatbelt-escape-gate.test.mjs` for the gate's verdict on recorded results and its refusal to run without its flag, which creates no launchd job.

## Conclusion

On macOS ALA runs every coding agent under a deny-by-default Seatbelt profile and refuses to run one without it. The guarantees are those of the profile, which follows paths where Bubblewrap changes the mount namespace, and each residual difference, the launchd residual above all, is stated here. The tests, the start probe and the escape gate check the profile's rules, the environment rule pairs and the launchd residual; residuals that follow only from the rules, such as a directory swapped on the host during a run, unix-socket binding, a stopped supervisor, Rosetta, `/Applications` and `Caskroom`, have no automated check.
