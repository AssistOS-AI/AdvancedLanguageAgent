## Introduction

[ALA](index.html) runs every request on a detected coding agent against caller-owned mounts.

## Core Content

Native terminal launches accept optional `systemPrompt` text through `buildNativeSessionLaunch` or `--system-prompt <text>` with `--native-interactive`. The value is limited to 16384 UTF-8 bytes and rejects NUL; omission, null in the embedding API, or an empty string preserves normal launch behavior. The value configures native instructions and never becomes a positional prompt, terminal input, or an automatic model turn. Each descriptor owns its native mapping: Codex uses a per-process `developer_instructions` override, Pi and OMP append a prompt file, Claude appends a system-prompt file, OpenCode adds an instruction path to its process-only configuration, Vibe selects a generated agent with additive instructions, and Antigravity selects a generated custom agent discovered through an additional directory. Generated files are private, read-only mounts under sandbox `/tmp`, with stable content-derived profile names and separate host temporary files per launch. ALA never installs these files in the working directory or shared agent home and cleans them after process exit or launch failure. Native base prompts remain agent-owned; supplied instructions take precedence in the native configuration fields they set. Callers must supply the same value when rebuilding a native launch.

ALA also exposes native Linux terminals through `ala --native-interactive --ca <name> [--cwd <folder>] [--home <folder>]`. This mode hands stdin, stdout and stderr to the native coding agent, defaults to the caller’s current directory, preserves the native exit status and writes no ALA transcript. It uses the shared Bubblewrap launcher with a private procfs and retains the terminal process group. `--native-arg <token>` and `--runtime-binary <absolute-path>` are repeatable; `--login-shell <absolute-path>` loads an explicitly selected login shell before exec. These options require native mode. Native mode refuses task prompts, payloads, controlled stdin, ALA session identifiers, result files, MCP configuration, model and effort overrides, and the ALA prompt loop with exit code 2; unavailable agents or sandbox support fail with exit code 5. `-i` and `--interactive` retain the existing ALA prompt loop. RoboWork supplies robot homes, explicit mounts and masks to ALA’s native launch builder and runner; ALA constructs and starts the coding-agent Bubblewrap process.

Version admission has no upper major-version ceiling. Pi/OMP, Claude Code and Vibe enforce their documented minimum releases; OpenCode 1 uses its legacy adapter and OpenCode >=2 uses the V2 adapter with served-API verification. Codex and Antigravity rely on their native protocol. A newer version is not refused solely because its major number increased, but incompatible protocol responses remain errors. Executables remain read-only inside execution sandboxes; managed installation updates happen outside the execution through RoboWork or the operator, rather than through an in-run self-updater.

ALA must provide four [generic execution capabilities](wiki.html#definition-generic-execution-capability): coding-agent execution, multi-step [agentic execution](wiki.html#definition-agentic-execution), web and research access, and temporary [task workspace](wiki.html#definition-task-workspace) creation. These capabilities describe how work runs; they must not embed translation, bibliography checking, controlled-language conversion, planning, or other domain methods.

Every execution, whether one-shot, interactive, explicit session, or controlled stdin, must run directly on a coding-agent backend through the coding-agent service (`src/coding-agents/service.mjs`). ALA has no other execution route and must not call model providers itself. The authenticated coding-agent CLI may perform multi-step synthesis, validation, research, transformation, or tool use. `--ca`/`--agent` defaults to `auto`. When no backend is detected, every execution must fail before doing any work with execution exit code `5` and the message `No coding agent is available. Install and authenticate Codex, OpenCode, Pi, OMP, Claude Code, Mistral Vibe, Antigravity CLI, or Antigravity CLI.`; a requested backend that is not available must fail with `Coding agent is not available: <name>` and exit code `5`. `ala agent list` must still succeed and report the detected backends, possibly none.

The standalone runtime must support Codex, OpenCode, Pi, OMP, Claude Code (`claude`), and Mistral Vibe (`vibe`), and Antigravity CLI (`agy`) as [coding-agent](wiki.html#definition-coding-agent) backends. Each process must detect the supported executables through `CODEX_BIN`, `OPENCODE_BIN`, `PI_BIN`, `OMP_BIN`, and `CLAUDE_BIN`, then standard user installation locations (`~/.local/bin/claude` for Claude Code) and `PATH`. Discovery must report backends in the fixed order Codex, OpenCode, Pi, OMP, Claude Code, Mistral Vibe, Antigravity CLI. Automatic backend choice must resume a session's saved backend; otherwise it must use the configured `codingAgent` when that backend is installed, and then the first available backend in the fixed order. The order is not configurable, and no environment variable overrides it. Every backend execution and model-catalog process must run in a sandbox that ALA selects by platform: a Bubblewrap namespace on Linux and a Seatbelt profile on macOS, which DS006 defines. No variable selects or disables a backend, and on any other platform ALA must fail with execution exit code `5`. On Linux, if `bwrap` is absent or cannot create the namespace, ALA must return execution exit code `5` and must not start the backend directly; on macOS the same exit code applies when `/usr/bin/sandbox-exec` is absent or the start probe fails. ALA never starts a backend without its sandbox. On Linux ALA uses `/usr/bin/bwrap` or `/bin/bwrap`, or only the absolute path in `ALA_BWRAP` when that variable is set, so a caller can ship a static Bubblewrap with the coding agents into a container that has none; an unusable `ALA_BWRAP` is a failure, not a reason to try another binary, and `ALA_BWRAP` has no effect on macOS. The private-procfs failure message names the container requirement (a new procfs in a user namespace, for Podman `--security-opt unmask=/proc/*`).

A one-shot process must create a new runtime for its request and must not import a selected coding backend, or native continuation from an earlier ALA process, except that explicit `--session-id` mode loads the pinned backend and native continuation from the session transcript defined in DS004. It must load current configuration and explicit orchestration paths at startup. An interactive process may retain runtime state across prompts, but once the first execution selects a backend it must pin later turns to that backend and pass only that backend's native continuation. These lifetimes must not be described as equivalent.

ALA must use supported non-interactive and native continuation interfaces and must not extract, copy, reinstall, or reinterpret credentials or coding-agent packages. ALA must query available models through a native adapter for each supported backend: Codex app-server `model/list`, `opencode models`, `pi --list-models`, and the Claude Code `initialize` control response, which lists model values, display names, and `supportedEffortLevels` without a model call. A backend-specific model persisted in `models` must be passed with the native model option on every invocation of that backend, including native continuation; when no value is configured, ALA must omit the option so the selected CLI uses its own default. Agent authentication and agent-native provider configuration remain owned by the selected CLI. `ala status` and interactive `/status` (`src/status-command.mjs`, `src/coding-agents/logins.mjs`) may only observe whether a login exists: a stored login is a credential file or OpenCode database row in the state directory the sandbox would mount for that backend (`CODEX_HOME`, `$XDG_DATA_HOME/opencode`, `PI_CODING_AGENT_DIR`, `CLAUDE_CONFIG_DIR`, or their defaults, all under an explicit `--home` when one is given), and an environment login is a set variable from that backend's credential allowlist. Detection must open only regular files of at most 4 MiB, never follow a symbolic link or block on a FIFO, never run a CLI or contact a provider, and never output, copy, or persist a credential value; only booleans and variable names leave the module. A reported login may be expired or revoked, and keychain logins are not detected. ALA must resolve the selected existing launcher and its interpreter or package prefix, bind that runtime read-only, and bind only the selected backend's known authentication, configuration, cache, and state directories read-write at controlled paths inside an otherwise temporary home. On macOS the same sources become read-only and read-write grants of the Seatbelt profile, and the controlled paths are links in a private home, or the folders themselves inside an explicit `--home`, as DS006 defines. On Linux, runtime prefixes below `/workspace` must use a private path under `/run/ala-agent-runtime` because the later task workspace bind would hide their original path. ALA must translate the selected executable and runtime search paths, preserve each prefix basename for Node package resolution, and retain existing paths for prefixes outside that overlay. Runtime path translation must not change the task cwd, controlled home, native continuation, or command arguments. Codex uses its controlled `CODEX_HOME`, Pi receives only its `.pi/agent` state and task session directory, OpenCode receives only its four configuration, cache, data, and state directories, and Claude Code receives only its configuration directory, the host's `CLAUDE_CONFIG_DIR` or `~/.claude` when no `--home` is given, as `CLAUDE_CONFIG_DIR=/home/ala/.claude`. That directory holds all Claude Code state, including the login and `.claude.json`. On macOS the variable names the same folder at its real path, and the sandbox gives no Keychain access, so Claude Code needs a credentials file in that folder or one of the allowed credential variables. Claude Code must use only Anthropic credentials, from its login or the allowed `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, and `CLAUDE_CODE_OAUTH_TOKEN` variables. Its sandbox must set `IS_SANDBOX=1`, because the sandbox may run as uid 0 and Claude Code refuses `bypassPermissions` as root otherwise, and `DISABLE_AUTOUPDATER=1`. A subscription-backed agent may satisfy a task without any provider API key in ALA. Failure after a backend process starts must not cause automatic failover because the temporary workspace may already contain partial work.

The Linux sandbox mounts the caller's writable `--cwd` at its canonical path (or `/workspace/<alias>`) and each read-only `--folder` at its canonical path, apart from controlled backend state. An explicit `--cwd` supplies the working tree and must persist; otherwise ALA creates and retains a private temporary workspace. An explicit `--home` supplies persistent backend configuration and authentication state. System executables, libraries, configuration, and the selected backend runtime must be read-only; the sandbox root must be remounted read-only after controlled binds; and the sandbox `PATH` must prefer the selected mounted runtime. ALA must clear the inherited environment and restore only fixed sandbox paths, terminal and locale values, network and certificate settings, backend controls, and supported provider credentials. `/tmp`, `/proc`, and `/dev` must be isolated, and unrelated host paths and environment secrets must be absent. A private procfs must be used when the host permits it, with an empty `/proc` fallback rather than caller procfs. ALA should create that procfs inside a private user namespace. In a capability-bounded nested container that permits a private PID namespace and procfs but blocks another user namespace from mounting procfs, ALA may use the outer capability only during Bubblewrap setup and must drop all capabilities before the coding agent starts. Codex and OpenCode must fail closed when neither private-procfs path is available. Networking remains shared. Every supplied directory is read-only unless the caller marks it `write`. The macOS sandbox grants the same directories read-write or read-only at their own paths, applies the same environment allowlist, gives each process a private temporary folder in place of the isolated `/tmp`, has no procfs to isolate, and shares the network, as DS006 defines.

Codex explicit sessions and ask-for-approval executions must use native app-server threads and turns; standalone full-access execution may use JSONL `exec` and `exec resume`. Both paths must retain native identity, expose intermediate progress, and render the final assistant answer once. App-server thread start and resume must request `approvalsReviewer:'user'`, `sandbox:'danger-full-access'`, and `approvalPolicy:'untrusted'` for ask mode or `'never'` for full access. Returned effective-policy refusals must be surfaced. ALA's sandbox remains the filesystem and process boundary; native full access must not start an incompatible second sandbox.

Codex command and file approvals must expose only valid native decisions and retain exact execution/network amendment response shapes. File requests must include available affected-item metadata. Permission-profile requests are separate: denial returns an empty profile with turn scope, while grants preserve exactly the requested profile and the chosen native turn/session scope. No grant may widen requested permissions. Native server-request resolution, turn completion, interruption, and process failure must dismiss matching host requests; user cancellation must interrupt the turn. Unsupported input or elicitation methods must fail visibly. Native session grants need not survive app-server recreation.

Pi must support only full-access and must require the verified 0.85.1-or-compatible RPC lifecycle before model work. Older executables must produce an actionable upgrade or `PI_BIN` configuration error; ALA must not upgrade global installations or install a permission extension. Explicit sessions use RPC session files, save identity before prompting, and wait for `agent_settled`, not the earlier `agent_end`. Cancellation uses `clear_queue` followed by `abort`. Assistant deltas, deduplicated textual tool updates, assistant error stops, and final-answer separation remain required.

Claude Code must require version 2.1.0 or newer, checked with `--version` before model work. ALA runs `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` and writes the prompt to standard input as a stream-json `user` record. A new conversation uses a UUID chosen by ALA with `--session-id`, and a continuation `{sessionId}` resumes it with `--resume`; the `init` record must report the requested session. A configured model goes to `--model` and a configured effort to `--effort`. `--MCPServers` entries must reach Claude Code as `--mcp-config` with `{"mcpServers":{name:{type:"http",url}}}` plus `--strict-mcp-config`, so Claude Code can use GUI and other MCP tools like Codex and OpenCode. Full access uses `--permission-mode bypassPermissions`. Ask-for-approval uses `--permission-mode default --permission-prompt-tool stdio`; each `can_use_tool` control request becomes an ALA permission request with Allow once and Deny, and a missing host denies the tool call. Live messages are written to standard input and reported as delivered, and the turn ends after the result for the last delivered message. Interruption sends the `interrupt` control request and then terminates the process. The `initialize`, `can_use_tool`, and `interrupt` control requests are the protocol the Claude Agent SDK uses with the same CLI; ALA depends on it and must fail visibly when a release no longer answers it.

OpenCode execution must own one authenticated loopback `serve` process inside the sandbox per execution. ALA parses its actual bound URL and verifies the executable version and served API before model work. V2 uses `/api/session`, enveloped responses, session model selection, queued prompts and execution events; V1 retains the unprefixed v1.15.10-or-compatible adapter. Native terminal full-access launch targets V2 with `--standalone --auto`. Session creation saves identity immediately; resume reads and updates that exact session without title lookup, export/import or forking. ALA subscribes before submitting the prompt and associates final text with its submitted message ID, never HTTP acceptance or historical idle. V2 history prefers `session_v2` when present; OpenCode itself owns database conversion. Connections belong to each server and are destroyed on stop because consecutive servers may bind the same port.

V2 MCP overlays use `mcp.servers`, model efforts use native variants in the session model request, and permissions use action/resource/effect rules with session-scoped replies. An absent saved native session fails without creating a replacement. RoboWork, rather than ALA, owns installation migration, original-state backups and activation gating. ALA transcripts and native continuation IDs remain unchanged by that migration.

OpenCode permission requests, including owned child-session requests, must map to native `once`, `always`, or `reject` replies. Session rules append ask/allow policy at turn boundaries and allow websearch and webfetch. Native question/plan denial remains separate from permission replies. Native Always rules must not leak into another active ALA execution. SSE failure, cancellation and control loss must abort the owned operation and stop the server. Web policy uses process-only `OPENCODE_CONFIG_CONTENT`; ALA must never rewrite project `opencode.json`. The fresh server password must remain private and absent from prompts, diagnostics and UI.

Coding-agent web search must always be enabled, with no CLI option, interactive command, or configuration field to disable it. Codex must run with `--search`, and app-server execution must receive `web_search="live"`. OpenCode must receive `OPENCODE_ENABLE_EXA=1` and permission rules that allow `websearch` and `webfetch`. Claude Code keeps its built-in `WebSearch` and `WebFetch` tools, which are on by default, and ALA must not disable them. Pi has no web search; ALA must not install or load a third-party extension for it and must leave Pi arguments and tools unchanged. Removing the switch keeps every execution on one search policy, so a resumed session cannot change tools between turns. Agent and search-provider authentication, quotas, rate limits, and source-site policy remain outside ALA.

Manual overrides must remain available without changing a task skill. Coding-agent authentication and model catalogs remain owned by the agent CLI, while ALA may persist the default backend and the user-selected backend model identifier and supported effort. `--model` must replace the selected backend's configured model for that invocation only and must drop the backend's configured effort when the model differs.

`--effort <value|default>` must override the selected coding agent’s configured effort for this invocation only. It applies to the backend selected by `--ca`, or by `auto` when `--ca` is omitted, and must preserve a resumed session’s backend. A native effort name must use letters, digits, underscores or hyphens and requires an effective model from `--model` or configuration. Native model metadata must validate support before execution. `--effort default` must clear configured effort even when the model stays unchanged. Without the option, configured effort is inherited unless `--model` changes the model. Model and effort arguments must not rewrite configuration. With `--home`, robot defaults come from that home unless an explicit configuration path overrides it.

Coding-agent reasoning effort is stored beside the model map as `efforts`, keyed by backend, in `.ala/config.json`. Each effort requires an explicit model. Native catalog metadata defines valid values: Codex `supportedReasoningEfforts`, Pi reasoning and `thinkingLevelMap`, OMP reasoning and `thinking` from `omp models --json` (its RPC model answer is limited to one 1 MiB frame, which a full catalog exceeds), connected OpenCode model variants, Claude Code `supportedEffortLevels`, Mistral Vibe `thinking_levels` from its effective configuration, and none for the Antigravity CLI, whose Gemini identifiers include the effort and reject `--effort`. Unsupported values fail with usage exit code 2 before a model turn. The interactive `/agent <name> effort <effort|default>` command persists or removes the effort of the backend's configured model; it requires a configured model, checks the native catalog before saving, and is cleared whenever `/agent <name> model` changes or resets the model. Codex exec receives `model_reasoning_effort`, Codex app-server receives `turn/start.effort`, Pi receives `--thinking`, OpenCode receives `prompt_async.variant`, Claude Code receives `--effort`, and Mistral Vibe receives `--thinking` when it starts a session, which then keeps it. These values apply to new and resumed executions, except that a resumed Mistral Vibe session keeps the model and thinking level it started with; omitted values preserve native defaults. Changing or clearing a model clears its effort override.

A failed turn keeps the coding agent's own error message and, when the agent's native protocol states why, adds that reason to the message as `[reason: …]`, with the provider HTTP status and the limit reset time when they are reported; the error also carries it as `failure` (`agent`, `code`, `reason`, optional `httpStatus` and `resetsAt`). Only structured native fields are read, never words of a message: Codex `codexErrorInfo` (for example `usageLimitExceeded`), Claude Code `rate_limit_event` records whose status is `rejected` and the result's `api_error_status`, and OpenCode `APIError` status codes and response-body error types such as `FreeUsageLimitError`, plus its authentication, context-overflow, output-length and content-filter errors. Pi, OMP, Mistral Vibe and Antigravity CLI report no such field, so their messages carry no reason. The generic formatting lives in `src/coding-agents/failure-reason.mjs` and each agent's reader in its own `failure.mjs`. Callers may display the reason but must not treat its absence as proof of any other cause.

## Conclusion

ALA preserves caller-owned working directories by running every request on an authenticated coding agent and fails explicitly when none is available.
