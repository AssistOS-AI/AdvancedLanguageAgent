## Introduction

[ALA](index.html) executes general requests through configured models and executes Anthropic task skills through detected coding agents. A [task repository](wiki.html#definition-task-repository) defines portable methodology without declaring an AchillesAgentLib skill family.

## Core Content

ALA must provide seven [generic execution capabilities](wiki.html#definition-generic-execution-capability): direct LLM execution, fast LLM execution, deep LLM execution, coding-agent execution, multi-step [agentic execution](wiki.html#definition-agentic-execution), web and research access, and temporary [task workspace](wiki.html#definition-task-workspace) creation. These capabilities describe how work runs; they must not embed translation, bibliography checking, controlled-language conversion, planning, or other domain methods.

All direct model work must pass through [AchillesAgentLib's](wiki.html#definition-achilles-agent-lib) [LLMAgent](wiki.html#definition-llm-agent) and runtime configuration. ALA must reuse compatible model tags and configured defaults. The generic model tiers are fast for inexpensive low-latency work, standard for ordinary language tasks, and premium or deep for quality-sensitive reasoning. Planning, coding, research, and long-context tags may add eligibility requirements.

Quality is a mandatory eligibility constraint. Straightforward general tasks should use direct model execution. Every selected Anthropic task skill must use an authenticated coding-agent CLI, which may perform multi-step synthesis, validation, research, transformation, or tool use as directed by `SKILL.md`.

The standalone runtime must support Codex, OpenCode, and Pi through a generic [coding-agent](wiki.html#definition-coding-agent) Code Skill. Each process must detect the supported executables through `CODEX_BIN`, `OPENCODE_BIN`, and `PI_BIN`, then standard user installation locations and `PATH`. The skill must be registered only when at least one backend is executable. Automatic backend choice must follow `ALA_CODING_AGENT_PRIORITY` before the persistent `codingAgents.priority` array and must otherwise use Codex, OpenCode, then Pi. Every backend execution and model-catalog process must run in a Linux Bubblewrap namespace; if `bwrap` is absent or cannot create the namespace, ALA must return execution exit code `5` and must not start the backend directly.

A one-shot process must create a new runtime for its request and must not import MainAgent conversation state, a selected coding backend, or native continuation from an earlier ALA process. It must load current configuration, repositories, and explicit orchestration paths at startup. An interactive process may retain runtime state across prompts, but once coding-agent execution selects a backend it must pin later coding-agent turns to that backend and pass only that backend's native continuation. These lifetimes must not be described as equivalent.

ALA must use supported non-interactive and native continuation interfaces and must not extract, copy, reinstall, or reinterpret credentials or coding-agent packages. ALA must query available models through a native adapter for each supported backend: Codex app-server `model/list`, `opencode models`, and `pi --list-models`. A backend-specific model persisted in `codingAgents.models` must be passed with the native model option on every invocation of that backend, including native continuation; when no value is configured, ALA must omit the option so the selected CLI uses its own default. Agent authentication and agent-native provider configuration remain owned by the selected CLI. ALA must resolve the selected existing launcher and its interpreter or package prefix, bind that runtime read-only at its existing path, and bind only the selected backend's known authentication, configuration, cache, and state directories read-write at controlled paths inside an otherwise temporary home. Codex uses its controlled `CODEX_HOME`, Pi receives only its `.pi/agent` state and task session directory, and OpenCode receives only its four configuration, cache, data, and state directories. A subscription-backed agent may satisfy a task when direct provider API keys are unavailable. Failure after a backend process starts must not cause automatic failover because the temporary workspace may already contain partial work.

The sandbox must use `/workspace` as its working directory and only writable project tree, apart from controlled backend state. An explicit `--cwd` supplies that tree and must persist; otherwise ALA creates and later removes it. An explicit `--home` supplies persistent backend configuration and authentication state. System executables, libraries, configuration, and the selected backend runtime must be read-only; the sandbox root must be remounted read-only after controlled binds; and the sandbox `PATH` must prefer the selected mounted runtime. ALA must clear the inherited environment and restore only fixed sandbox paths, terminal and locale values, network and certificate settings, backend controls, and supported provider credentials. `/tmp`, `/proc`, and `/dev` must be isolated, and unrelated host paths and environment secrets must be absent. A private procfs must be used when the host permits it, with an empty `/proc` fallback rather than caller procfs. ALA should create that procfs inside a private user namespace. In a capability-bounded nested container that permits a private PID namespace and procfs but blocks another user namespace from mounting procfs, ALA may use the outer capability only during Bubblewrap setup and must drop all capabilities before the coding agent starts. Codex and OpenCode must fail closed when neither private-procfs path is available. Networking remains shared. Every selected task skill must use a strict read-only bind under `/workspace/.agents/skills/<name>`.

Codex must run through JSONL `exec` or `exec resume`, retain the native thread identifier, expose completed command text and assistant messages known to be intermediate as interactive progress, and reserve the last completed assistant message for the normalized result so it is rendered only once. Because ALA already places the complete Codex process inside its Bubblewrap boundary, ALA must select Codex's `danger-full-access` policy to prevent Codex from creating an unsupported second user-namespace sandbox. This policy grants no access beyond the filesystem, process, capability, and environment boundary already established by ALA. Benign stdin notices and stale-rollout catalog diagnostics must not become successful-turn output. Pi must run through its JSON event mode with an explicit session identifier and task session directory, expose assistant deltas and deduplicated textual tool updates, detect assistant error stops, and select the completed assistant message as the normalized result. OpenCode must expose its native run output interactively, identify a new session by unpredictable title and exact sandbox project directory with a read-only database fallback, export the session, and select its last assistant text as the normalized result. Control output from model listing, session discovery, and session export must not appear as user-visible progress.

Coding-agent web search must be controlled by one shared Boolean runtime value. It must default to disabled, accept bare `--websearch` as an invocation-only enable flag, accept `--websearch on|off` as an explicit invocation-only override, and accept interactive `/websearch on|off` as an immediately applied persistent update. ALA must translate enabled state to Codex native live search and OpenCode web-search and web-fetch permission with its Exa integration enabled. Disabled state must explicitly disable Codex search and deny OpenCode web-search and web-fetch tools. Pi has no ALA-managed web-search capability: ALA must not install or load a third-party extension and must leave Pi arguments and tools unchanged regardless of this setting. Agent and search-provider authentication, quotas, rate limits, and source-site policy remain outside ALA.

Provider names, model identifiers, and mappings from tags to concrete executors are runtime configuration for direct model work. Manual overrides must remain available without changing a task skill. Coding-agent authentication and model catalogs remain owned by the agent CLI, while ALA may persist only the user-selected backend model identifier and shared web-search Boolean. The direct-execution `--model`, `--tag`, `--reasoning-effort`, `--model-config`, and their environment-derived LLMAgent values must not be forwarded or reinterpreted as coding-agent configuration.

## Conclusion

ALA preserves portable Anthropic task skills by executing them through authenticated coding agents while keeping general model work inside configured AchillesAgentLib components.
