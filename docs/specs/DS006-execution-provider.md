## Introduction

An [execution provider](wiki.html#definition-execution-provider) is the only component through which [ALA](index.html) starts a native process. ALA describes each process it needs, and the provider either satisfies the request or refuses it. This specification owns the provider interface, its versioned wire protocol, provider selection, and the conformance tests that any provider implementation can run. The embedding service that implements the server side of the protocol is outside this repository, and ALA imports nothing from it, parses none of its configuration, and names none of its products.

## Core Content

### Providers and selection

There are two providers. The Bubblewrap provider (`src/coding-agents/provider-bubblewrap.mjs`) holds the standalone Linux Bubblewrap launch, moved behind the interface without any change to its argument vector, working directory, environment merge, or fail-closed checks; it is the default. The protocol client (`src/coding-agents/provider-client.mjs`) speaks the wire protocol below over one control channel that the embedding service passes at launch. A provider is an object with a string `kind` and a `start(request)` function that returns a child-process-like object (`stdin`, `stdout`, `stderr`, `kill`, `exitCode`, and the `error`, `exit` and `close` events); it may also offer `inventory()`, `tempdir()`, `connect()` and `close()`.

The embedding service selects the provider explicitly with `--execution-provider bubblewrap|protocol` or `ALA_EXECUTION_PROVIDER`; the option wins. A value outside that set, including an empty value, is a usage error with exit code `2`. Without a selection the Bubblewrap provider is used. Nothing is auto-detected: a connected control channel selects nothing. Selecting `protocol` constructs no Bubblewrap provider, so embedded mode never runs the Bubblewrap capability probes, which otherwise run when the Bubblewrap provider is constructed. Selecting `protocol` without a connected control channel fails with exit code `5` and the message `The execution-provider descriptor is missing`, and ALA never falls back to the Bubblewrap provider.

Process creation exists only inside provider implementations. `spawnProcess` delegates to the provider carried by the execution context and fails with exit code `5` when there is none; there is no direct-start branch and no skip-sandbox mode. A spawn function injected by a test is honored only when the provider is not the protocol provider, and the production code paths never inject one. `src/` imports `child_process` only in the Bubblewrap provider and in the Bubblewrap capability probe, and a static test enforces it.

### The launch description

The in-process description of a launch carries the process class, the executable, the arguments, the environment, the working directory, the standard-stream plan and the execution context (backend, HOME, folders and exclusions). Process classes are `run` (one-shot to exit, such as `codex exec`, a version check or `opencode models`), `session` (a long-lived standard-stream peer, such as `codex app-server`, Claude Code stream-json or Pi RPC), and `service` (a server reached by connection, such as `opencode serve`). The adapters set the class, and an unknown class is an execution error.

### Wire protocol, version 1

The protocol carries JSON messages on a Node.js IPC channel (the default `json` serialization, so the embedding service launches ALA with an `'ipc'` stdio entry and no `advanced` serialization). The control channel is the `process` object when ALA was started with an IPC channel, and its messages are objects with a string `type`. Standard streams and service connections are not encoded in messages: the provider passes each as a connected socket in the handle slot of a message, which is how the channel passes a descriptor, and the client wires that socket to the child-process-like object. A provider must pass the end of a socket pair that it has not read, for example one accepted with `pauseOnConnect`, because a sender that reads or closes its end can consume bytes or the end-of-stream before the receiver owns it. The client sends no message other than `hello` until the provider's `hello` has arrived, fails every operation when the handshake does not finish within 10 seconds, and on `close()` sends a `stop` for a running process only after the handshake completed. The client never sends a handle with a message, and a provider must reject, with a channel-wide `failure`, a client message that carries a handle or has a type outside this table.

A provider delivers every stream that the request asked for (`stdout` and `stderr` always, `stdin` when the request asked for a piped input) before it sends `exit`, and sends `started` without a handle. A `stream` message after the process's `exit`, a handle attached to `started`, and a second delivery of one stream are protocol violations. Time limits apply only to answers, never to process lifetimes: the answer to `inventory`, `tempdir` and `connect`, and the `started` or `refused` answer to a `start`, must each arrive within the request timeout (30 seconds by default), otherwise that operation fails with an explicit execution error (`did not answer the <operation> request`), and a start that timed out is stopped with `graceMs` `0`. A result that arrives after its request timed out is ignored. A running process has no lifetime limit in the client; a deadline is recorded execution policy in the start request. A write error on the control channel, reported through the send callback or an `error` event on the channel, fails every operation with exit code `5` like a closed channel.

| Direction | Message | Meaning |
| --- | --- | --- |
| client to provider | `{type:'hello', protocol:'ala-execution-provider', versions:[1]}` | First message. The provider answers `hello` with the version it speaks. |
| provider to client | `{type:'hello', protocol:'ala-execution-provider', version:1}` | A different protocol name or version fails every operation with an explicit execution error. |
| client to provider | `{type:'start', process:<n>, request:<start request>}` | Starts one process. `<n>` is chosen by the client from 1 upward and names the process in every later message. |
| provider to client | `{type:'started', process}` or `{type:'refused', process, error:{code,message}}` | The provider satisfied or refused the request. A refused process never starts. |
| provider to client | `{type:'stream', process, stream:'stdin'\|'stdout'\|'stderr'}` plus a socket | Delivers one standard stream. `stdin` is delivered only when the request asked for a piped input. |
| client to provider | `{type:'stop', process, graceMs}` | Ends the exact process tree: `SIGTERM` and `SIGINT` map to the request's stop grace, `SIGKILL` to `0`. |
| provider to client | `{type:'exit', process, code, signal}` | The process ended. The client reports `close` after the exit and the end of both output streams. |
| provider to client | `{type:'failure', process?, error}` | A provider failure for one process, or for the whole channel when `process` is absent. ALA reports it as `Execution provider failed: <text>`, distinct from a refusal (`Execution provider refused the request: <text>`). |
| client to provider | `{type:'inventory', id}` | Asks for the backends of the image's tool inventory. The answer is a `result` whose value is a list of `{name, version?}` with names from `codex`, `opencode`, `pi`, `claude`. |
| client to provider | `{type:'tempdir', id}` | Asks for a private temporary directory in the workload view. The answer is a `result` whose value is `{path}`, a normalized absolute virtual path other than `/`. |
| client to provider | `{type:'connect', id, process, endpoint}` | Asks for one connected stream to a service of the same execution. `endpoint` is `{kind:'loopback-port', host:'127.0.0.1', port}` or `{kind:'unix-socket', path}`. The answer is a `result` that carries the socket. |
| provider to client | `{type:'result', id, ok:true, value}` or `{type:'result', id, ok:false, error:{code,message}}` | Answers `inventory`, `tempdir` and `connect`. |

A provider's obligations are the same for every implementation. It resolves `executable` only against the image's tool inventory (the answer to `inventory`) and never through ALA's `*_BIN`, `PATH` or HOME discovery; a path under HOME or a project runs only as robot code, never as the backend. It applies `env` only at the final exec and sets its own variables (HOME, the XDG directories and the native state paths) so that additions cannot override them. It adds `exclusions` to its own mandatory exclusions and never subtracts one, and it refuses a request whose exclusion it cannot enforce. It maps `network` to its connection matrix and never grants a wider one. It always provides a private `/proc` and refuses a requirement it cannot meet. It creates Pi's per-session directory on the workload side, under HOME, because ALA creates no directory on the host. The start request contains exactly these fields. `processClass` is `run`, `session` or `service`. `executable` is a backend name from the inventory or an absolute path inside the workload view; embedded ALA sends the backend name only. `args` is the argument vector, passed unchanged to the final exec. `env` holds additions by name, and the provider applies them only at the final exec. `home` is the robot HOME token `/home/robot`. `cwd` is a virtual path. `folders` is a list of `{path, access}` with access `read` or `write`. `exclusions` is a list of virtual paths that must be absent. `communication` is `{kind:'streams', stdin:'pipe'|'ignore'}` or, for a service, `{kind:'service', endpoint:'loopback-port', stdin}`. `lifecycle` is `{stopGraceMs, deadlineMs?, ready?}`, where a service carries `ready:{condition:'announced-endpoint', timeoutMs}`; a deadline is recorded execution policy, not a transport timeout. `network` is `robot-egress` or `none`. `requirements` is `{privateProc:true}`. A provider refuses a request it cannot satisfy and never weakens it: a class it does not know, a path outside the admitted view, folders that are not a subset of the admitted grants at equal or lower access, an environment name outside its allowlist, or an exclusion it cannot enforce.

Embedded ALA starts with a cleared environment, and only explicit additions cross the protocol. The base is the environment the CLI was given. An addition is an entry of the launch environment whose value differs from that base, so a value that merely exists in ALA's process, such as a credential, is never forwarded, and an entry whose value equals ALA's own is treated as inherited and dropped. The only exception is a name that an adapter generates itself; it is forwarded even when it equals an inherited value. For OpenCode in embedded mode an inherited `OPENCODE_CONFIG_CONTENT` is ignored and the overlay is built fresh, so nothing from ALA's environment crosses, and the one deliberate crossing is the per-server `OPENCODE_SERVER_PASSWORD` that ALA generates and sends only in the start request of the server it launches. Standalone behaviour is unchanged. The client rejects `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH`, `TMPDIR`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR` and every `XDG_` name, because the provider owns them: the provider must set HOME, the XDG directories and the native state paths (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`) in agreement under `/home/robot`. ALA adds the backend controls that its standalone sandbox environment sets and the provider cannot know, as explicit additions keyed on the backend: `IS_SANDBOX=1` and `DISABLE_AUTOUPDATER=1` for Claude Code, so that `bypassPermissions` is accepted as root and no updater runs, and `PI_OFFLINE=1` and `PI_SKIP_VERSION_CHECK=1` for Pi. Text that arrives from a provider is untrusted: the client strips control characters and bounds the length before any message reaches a user, and a malformed message, an unknown message type, a stream without a socket, or a message for an unknown process is a protocol violation that fails every operation on the channel. A closed channel, a provider crash, a refusal, an unsupported version and a silent provider each fail the affected operation of every process class and of the inventory query with exit code `5`; ALA never starts the process itself.

A service is reached only through the provider. After the server announces its loopback port on a standard stream, ALA asks the provider for a connection per HTTP exchange, and the OpenCode HTTP client takes a connection factory (`createOpenCodeHttpClient({connect})`) that hands each provider socket to `node:http` through the asynchronous form of the agent's `createConnection`. The Bubblewrap provider offers no `connect`, because it shares the network namespace, and the client then opens its own loopback sockets as before.

### Embedded mode

Embedded mode is an execution whose provider is the protocol provider. The provider owns the filesystem the workload sees, so ALA performs no operation on workload paths. `--home` is the virtual path `/home/robot` or absent; `--cwd` and each `--folder` are normalized absolute virtual paths that ALA never canonicalizes, stats or creates, and `--ignore` paths become exclusions. A folder may not be the root or overlap the robot HOME or another folder, and a read-only ancestor may contain the writable working directory as in standalone mode. Without `--cwd` ALA asks the provider for a private temporary directory. The aliases `--cwd as` and `--folder as|at|expose` name Bubblewrap mount layout and are refused, because the provider mounts fixed workload paths itself. `--file`, `--url`, `--taskFile` and `--output` are refused; prompt text and payload text reach ALA over the control stream (`--task`, `--text`, `--stdin`, or the first control record). Backends are discovered only through the provider's inventory and referred to by name, and `ala agent list` and `ala agent models` use the inventory and a provider temporary directory.

Embedded execution requires `ALA_SESSIONS` to name an absolute private session directory, so a transcript can never default into the writable working directory, and requires `--config` to name an existing absolute managed configuration file. The managed configuration is read-only: interactive `/agent use`, `/agent <name> model` and `/agent <name> effort` fail with a usage error before writing (the interactive loop reports it and continues), and so do `/status` and `ala status` (exit code `2`), because login detection reads credential files that the orchestration domain cannot see. Pi keeps its native session files in `.ala-pi-sessions` under the provider HOME, and ALA creates no directory for them on the host.

### Conformance

ALA owns the conformance tests, and a server implementation consumes them from the pinned ALA source by file path, importing `tests/provider-conformance.mjs` (and using `tests/fake-provider.mjs` as the reference server); the package `exports` are unchanged and expose only the transcript readers. `tests/provider-conformance.mjs` drives any provider through the interface only, given a harness that supplies the provider and deterministic fixtures: a one-shot process with output and exit status, a non-zero exit, a standard-input echo session, a process that runs until stopped, a refused request outside the admitted view, and a loopback service reached through provider connections. Its raw-wire mode (`defineRawWireConformance`) sends crafted `start` messages below the client so that a server's own admission decisions are tested: an unknown class, an executable path or a backend outside the inventory, a HOME other than `/home/robot`, a working directory outside the view, a folder outside the grants or a write folder over a read-only grant, a provider-owned or XDG variable, an exclusion that cannot be enforced, a wider network and a missing private `/proc` must each be answered `refused` or `failure` and never `started`, and a message with a handle or of an unknown type must be rejected. `tests/fake-provider.mjs` is a deterministic in-memory provider server with setup-failure, failure-after-start, channel-wide failure, silent and write-error modes, `tests/provider-protocol.test.mjs` and `tests/provider-ipc.test.mjs` run the suite and the failure matrix against it and over a real IPC channel, `tests/provider-opencode.test.mjs` drives the OpenCode `run` and `service` lifecycle through it, `tests/provider-bubblewrap.test.mjs` pins the unchanged standalone launch, and `tests/provider-static.test.mjs` pins the process-creation and import boundaries.

## Conclusion

Every native process starts through a provider that the caller selected explicitly, standalone ALA keeps its unchanged Bubblewrap launch, and embedded ALA speaks one versioned protocol, touches no workload path, and fails closed.
