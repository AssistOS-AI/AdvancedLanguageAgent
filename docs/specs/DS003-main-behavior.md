## Introduction

[Advanced Language Agent (ALA)](index.html) lets a human or calling agent submit a language-oriented task through the `ala` command and receive the requested result without integrating a model provider, sandbox, or [coding agent](wiki.html#definition-coding-agent) directly. This specification contains the implemented behaviors that determine that user outcome.

## Core Content

### Main Behavior Components

| Name | Explanation |
| --- | --- |
| Single-shot and interactive request execution | A human or agent supplies an instruction and optional payloads, and ALA returns a clean result once or across a retained interactive session. |
| Coding-agent selection | ALA detects installed Codex, OpenCode, Pi, and Claude Code CLIs, picks the backend for every execution from `--ca` or `auto`, and fails with exit code `5` before any work when no usable backend exists. |
| Sandboxed coding-agent execution | ALA runs the request on the selected agent CLI, starts every agent process through its Bubblewrap execution provider by default, and mounts exactly the caller-supplied `--cwd` and `--folder` directories at their canonical or aliased paths. |
| Embedded execution through an execution provider | An embedding service selects `--execution-provider protocol`, and ALA then asks that service's provider to start every agent process on virtual paths, builds no sandbox, and fails with exit code `5` instead of starting a process itself or falling back to Bubblewrap. |

### Single-shot and interactive request execution

A human or calling agent starts this behavior with `ala [options] [instruction...]`. ALA must combine positional instruction text with ordered `--text`, `--file`, `--url`, and `--stdin` payloads, and also accept orchestration-oriented `--task` or `--taskFile` prompts. Each process builds a new runtime. Explicit `--session-id` and `--resume-session` preserve the native coding-agent conversation across processes, and ALA records each such conversation in an append-only [session transcript](wiki.html#definition-session-transcript) at `$ALA_SESSIONS/sessions/<uuid>.jsonl`, defaulting to `<cwd>/.ala`, which embedding applications read through the `advanced-language-agent/transcript` package export. `--resume-session` takes the native continuation from that transcript. Ordinary one-shot execution has no implicit continuation and writes no transcript. Coding-agent execution uses the explicit `--cwd` directory when supplied and otherwise creates and retains a private temporary workspace. `--home` selects the coding-agent configuration home. During an interactive session, lines beginning with `/` are local commands; arbitrary folder-mount commands are not supported.

The observable result must contain only the requested content on standard output or in the file selected by `--output`. Diagnostics, interactive prompts, and supported live coding-agent events must use standard error. While terminal input and standard error are both interactive, every coding-agent wait must display a repeating `Thinking.`, `Thinking..`, and `Thinking...` status on one diagnostic line. The first live coding-agent event must clear and stop that indicator before visible assistant, command, tool, or native provider output is written, while the normalized final answer remains the standard-output result. The status must clear on success, failure, or interruption and remain disabled for redirected or non-interactive streams. ALA must refuse to replace an existing output file unless the caller supplies `--force`, limit each file or URL payload to 10 MiB, limit their aggregate size to 32 MiB, stop URL retrieval after 30 seconds, and convert interruption into exit code `130`. These hidden protections prevent an accepted request from consuming unbounded input, contaminating machine-readable output, or silently destroying an existing result file. DS004 defines the detailed session and input contracts.

### Coding-agent selection

Every one-shot, interactive, explicit-session, and controlled-stdin execution runs directly on a coding-agent backend through the coding-agent service in `src/coding-agents/service.mjs`; ALA has no other execution route and calls no model provider itself. At process startup ALA detects Codex, OpenCode, Pi, and Claude Code through `CODEX_BIN`, `OPENCODE_BIN`, `PI_BIN`, `CLAUDE_BIN`, standard installation locations, and `PATH`; when an embedding service's execution provider is selected, ALA instead takes the backends from the provider's tool inventory and detects nothing in its own filesystem. `--ca auto|codex|opencode|pi|claude` is the orchestration-facing selector, `--agent` remains its compatibility spelling, and it defaults to `auto`. `auto` resumes a session's saved backend, otherwise selects the configured `codingAgent` when installed, otherwise the first available of Codex, OpenCode, Pi, Claude Code. When no backend is detected, every execution must fail before opening a session, creating a workspace, or starting a process, with exit code `5` and the message `No coding agent is available. Install and authenticate Codex, OpenCode, Pi, or Claude Code.` A requested backend that is not available must fail with `Coding agent is not available: <name>` and exit code `5`. This hidden check prevents a request from being silently accepted without an executor. `--model` replaces the selected backend's configured model for one invocation and drops its configured effort when the model differs.

The runtime must forward interruption to the active backend, normalize the returned result, and close the coding-agent service when execution ends. Research access, general task-workspace requests, and [Ploinky](wiki.html#definition-ploinky) hosting remain specialized contracts in DS002, DS004, and DS005.

### Sandboxed coding-agent execution

A human or calling agent runs a bounded request on the selected [coding agent](wiki.html#definition-coding-agent). The default standalone [execution provider](wiki.html#definition-execution-provider) is Bubblewrap: every agent process starts through it, and the mount, alias and sandbox rules in this chapter describe it (DS006 defines the provider interface). `ala agent list` must report available Codex, OpenCode, Pi, and Claude Code executables in that fixed order without starting a model session, and it succeeds with empty output when none is detected. Interactive `/agent use <codex|opencode|pi|claude>` must save `codingAgent` as the default backend for later automatic selection. Interactive `/agent <name> models` must list identifiers from the selected backend's native catalog, `/agent <name> model <model-name>` must persist and immediately apply that backend's selection, and `/agent <name> model default` must delete the persisted override and immediately restore native agent-default selection. Both model commands clear that backend's configured effort. `--session-id` without `--ca` behaves as `--ca auto`.

`ala status [--json] [--home <path>] [--config <path>]` and interactive `/status` report, without starting a coding agent, whether each backend is installed, whether it holds a stored or environment login, found passively as DS002 defines, and which backend `--ca auto` would choose; `--json` returns `{codingAgent, configuredAgent, agents: [{name, available, binary, loggedIn, login: {file, env}}]}` and never contains a credential value.

`ala agent models <codex|opencode|pi|claude> [--json] [--home <path>]` lists one agent's native model catalog without opening a conversation, through the same sandboxed query as interactive `/agent <name> models`, in a private temporary working directory that it removes afterwards; text output prints one model identifier per line, `--json` returns `[{id, efforts, defaultEffort?}]` with the efforts each model advertises, `--home` selects the agent's authentication home as for executions, and an unavailable agent fails with exit code 5.

Web search must always be enabled for Codex and OpenCode through their native controls and for Claude Code through its built-in `WebSearch` and `WebFetch` tools, and ALA must offer no option or command that disables it. Pi has no web search, and ALA must not add a third-party capability for it. ALA must not persist search credentials or bypass provider or source-site limits.

ALA implements and distributes no runtime skills. It mounts exactly the caller-supplied directories: the writable `--cwd <path> [as <alias>]` and each read-only `--folder <path> [as <alias>|at <absolute-path>] [expose]`, or read-write with `write`. Without an alias a directory is mounted at its canonical absolute path; an alias mounts it under `/workspace/<alias>`. When `--cwd` is omitted ALA creates and retains a private temporary workspace. An explicit `--home` supplies persistent backend configuration and authentication state. ALA preserves the backend's native continuation inside a session and never deletes a caller-supplied or temporary working directory. The installed backend and runtime are mounted read-only and are never installed into the mounted directories. ALA must validate and mount the supplied directories without interpreting their configuration or communication protocols, and it must not discover or prepare task skills or infer their mounts. Caller-supplied `--ignore` directories remain inaccessible behind empty read-only sandbox mounts, including ordinary aliases. Callers may explicitly overlay read-only directories and export selected subdirectories of ignored sources while retaining private parent masks. DS004 defines validation and visibility. DS002 and DS004 define backend and mount details.

### Embedded execution through an execution provider

An embedding service, such as a worker that builds the sandbox for every execution itself, starts `ala` with one Node.js IPC control channel and selects `--execution-provider protocol` or `ALA_EXECUTION_PROVIDER=protocol`. The option or variable is the only selector: a connected channel selects nothing, any other value is a usage error with exit code `2`, and a missing channel fails with exit code `5`. ALA then sends every `run`, `session` and `service` process request, including OpenCode's loopback server, to the provider over the versioned wire protocol in DS006, builds no Bubblewrap sandbox, runs no Bubblewrap probe, and never starts a process itself. A refused request, an unsupported protocol version, a provider failure, or a closed channel ends the affected operation with exit code `5`.

In this [embedded mode](wiki.html#definition-embedded-mode) `--home` is `/home/robot`, and `--cwd`, `--folder` and `--ignore` are virtual paths that ALA never canonicalizes, checks, or creates. The execution requires an existing absolute `--config` and an absolute `ALA_SESSIONS`, and it refuses `--file`, `--url`, `--taskFile`, `--output`, the `--cwd as` and `--folder as|at|expose` aliases, `ala status`, and the interactive commands that would change the stored backend, model or effort. These refusals keep an untrusted workload from steering ALA's own files and keep the managed configuration read-only.

## Conclusion

ALA fulfills its purpose by accepting single-shot and interactive requests and running every request on a detected authenticated coding agent against caller-owned mounts, standalone through its Bubblewrap provider or embedded through a service's provider, failing explicitly when no agent or provider is available, while preserving clean output and bounded lifecycle behavior.
