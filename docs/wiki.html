Advanced Language Agent Wiki

This page is the canonical reference for specialized project terminology. Each entry explains one concept and links only to different concepts needed to understand its relationships.

Generic execution capability

A generic execution capability describes how ALA can run work without embedding a domain-specific method. The architecture recognizes authenticated coding-agent execution, multi-step agentic execution, web and research access, and temporary workspace creation.

Every request runs on a detected coding agent that can apply its own tools inside the sandbox. Availability depends on the installed and authenticated executors; a named capability does not guarantee that every deployment supplies a matching backend.

Coding agent

A coding agent is a supported authenticated command-line agent that can plan, use tools, validate intermediate work, and return a final response for a bounded ALA request. The standalone runtime supports Codex, OpenCode, Pi, and Claude Code (claude). Although these tools can edit code, ALA uses them as general executors for language, research, planning, verification, transformation, and bounded code-fragment tasks.

ALA detects their executables when each process starts and runs every execution on one of them; when none is available, every execution fails before any work with exit code 5. The agent keeps ownership of its authentication, provider configuration, model catalog, and search-provider limits, while ALA may persist a default backend and one user-selected native model and effort per backend. ALA runs every backend and model-list process inside Linux Bubblewrap and mounts exactly the caller-supplied --cwd and --folder directories at their canonical paths, or under a caller-chosen alias, exposing only controlled runtime and authentication/state paths and leaving other host paths absent. An explicit --home owns persistent agent configuration. It always enables web search for Codex and OpenCode through their native controls, leaves Claude Code's built-in web tools on, retains the agent's opaque native continuation during an interactive session, and mounts only what it was given. Pi has no web search, and ALA does not add an extension for it.

Native permissions are the selected agent's rules for approving its own operations. ALA's ask-for-approval mode forwards Codex app-server, OpenCode server, or Claude Code can_use_tool requests to a reply-capable host; full-access removes those native prompts without removing Bubblewrap. Pi supports full-access only. The host displays the native choices and returns an opaque option identifier, while ALA retains the exact native answer payload. No host approval cache replaces the backend's policy, and native remembered grants need not survive a recreated backend process.

Execution routing

Execution routing selects the coding agent backend on which an execution runs. Every one-shot, interactive, session, and controlled-stdin execution uses a coding agent; --ca/--agent defaults to auto, which resumes a session's saved backend, otherwise uses the configured codingAgent when installed, otherwise the first available backend in the fixed order Codex, OpenCode, Pi, Claude Code.

ALA fails with exit code 5 when no backend is available or when the requested backend is not available. --model overrides only the selected backend's native model for one execution.

Agentic execution

Agentic execution is a bounded multi-step mode in which an eligible agent may plan, invoke tools, retry, validate, and synthesize a result. It is intended for work whose procedure cannot be completed adequately by one straightforward model call.

Retry limits and escalation policy must remain finite; ALA does not expose a separate command that directly selects this mode.

Task workspace

A task workspace is the directory tree a coding-agent execution can read and write. ALA binds the caller's explicit --cwd, or a retained temporary directory when it is omitted, read-write at its canonical path or under /workspace/<alias> inside Bubblewrap.

A task workspace is not an implicit copy of the caller's source repository and does not give ALA general ownership of that repository. Additional read-only or explicitly writable directories are supplied through --folder <path> [write] [as <alias>|at <absolute-path>] [expose]. ALA mounts exactly what it is given and does not discover or prepare caller task skills; it mounts only explicitly supplied directories.

Session transcript

A session transcript is the append-only JSONL file in which ALA records one persistent coding-agent conversation started with --session-id. ALA owns the file and writes it at $ALA_SESSIONS/sessions/<uuid>.jsonl; when ALA_SESSIONS is unset the directory is <cwd>/.ala, and a relative value resolves against --cwd. Executions without --session-id have no transcript.

The first line is a session record. Each turn then adds a user record with the user's own text, agent-message records with visible coding-agent output buffered per output stream, a final record with the result, and a turn-end record with status completed, failed, or interrupted. Follow-up messages accepted through control stdin become further user records of the same turn. Every record carries seq, type, and at, and turn records also carry turnId, which the caller can set with --turn-id.

continuation records hold the pinned backend and its opaque native continuation. The last one wins, and --resume-session reads it to reopen the backend's own conversation. The transcript does not replace backend state. Codex, OpenCode, Pi, and Claude Code still keep their native history, under --home or, for Pi, in <workspace>/.ala-pi-sessions.

ALA never rewrites a line, so an interrupted append can leave only a trailing partial line, which readers ignore. A .lock file beside the transcript lets one ALA process write at a time. Embedding applications read transcripts through the advanced-language-agent/transcript package export and must not depend on parsing the files themselves. With the default location the transcript lies inside the writable task workspace, so the coding agent can see it; set ALA_SESSIONS outside the mounted directories to keep it out of the sandbox.

Ploinky

Ploinky is an external agent-hosting environment described by ALA's integration contract. A deployment may expose ALA operations through Ploinky interfaces or use a Ploinky agent as an executor when its advertised capabilities match the request.

ALA remains a standalone CLI and must not require Ploinky. Concrete hosting and remote-agent protocols remain integration contracts outside the implemented standalone runtime.

WebChat

WebChat is the Ploinky browser conversation interface through which a hosted ALA agent may receive task requests. It is an optional integration surface and does not replace the standalone ala command.

The ALA repository defines the shared request and result contract but does not own WebChat transport. Ploinky owns authentication, session transport, and browser hosting behavior.
