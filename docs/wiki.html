Advanced Language Agent Wiki

This page is the canonical reference for specialized project terminology. Each entry explains one concept and links only to different concepts needed to understand its relationships.

AchillesAgentLib

AchillesAgentLib is the external JavaScript library installed under the package identity ploinky-agent-lib. ALA uses it for MainAgent, LLMAgent, model tags, sessions, cancellation, and the internal Code Skill that bridges MainAgent to coding-agent execution.

ALA resolves the library from an explicit path, the ACHILLES_AGENT_LIB_PATH environment value, a sibling checkout, or the package dependency. Model providers and concrete model identifiers remain AchillesAgentLib configuration. ALA passes supported overrides to the library and does not reimplement provider credentials or model invocation.

Discovery registry

The discovery registry is a process-scoped temporary directory created by ALA for AchillesAgentLib. It exposes only ALA-owned generic runtime skills, including the internal coding-agent bridge, to one MainAgent.

ALA removes the registry when runtime creation fails or when execution closes. ALA never scans a caller workspace for task descriptors; callers install their own task methods in their own directories.

MainAgent

MainAgent is the AchillesAgentLib coordinator that ALA creates for each runtime. It receives the discovery-registry path, prepares available skills, retains the active conversation, and executes prompts through its configured LLMAgent and supported skill subsystems.

MainAgent executes general requests and invokes ALA's internal coding-agent bridge. ALA forwards cancellation to MainAgent and shuts it down before removing the temporary registry.

LLMAgent

LLMAgent is the AchillesAgentLib class through which ALA's model-backed work runs. It resolves an explicit model, semantic tags, reasoning effort, and configured defaults into an eligible provider invocation.

ALA supplies command-line or environment overrides but does not call providers outside LLMAgent. If no model is explicitly selected, AchillesAgentLib applies its configured defaults, which may point to Soul Gateway or another provider.

Generic execution capability

A generic execution capability describes how ALA can run work without embedding a domain-specific method. The architecture recognizes direct, fast, and deep model execution, authenticated coding-agent execution, multi-step agentic execution, web and research access, and temporary workspace creation.

General requests may use direct model services, while coding-agent work uses a detected coding agent that can apply its own tools inside the sandbox. Availability depends on configured providers and installed executors; a named capability does not guarantee that every deployment supplies a matching backend.

Coding agent

A coding agent is a supported authenticated command-line agent that can plan, use tools, validate intermediate work, and return a final response for a bounded ALA request. The standalone runtime supports Codex, OpenCode, and Pi. Although these tools can edit code, ALA uses them as general executors for language, research, planning, verification, transformation, and bounded code-fragment tasks.

ALA detects their executables when each process starts and registers a generic Code Skill when at least one is available. The agent keeps ownership of its authentication, provider configuration, model catalog, and search-provider limits, while ALA may persist one user-selected native model identifier per backend and one shared Boolean web-search setting. ALA runs every backend and model-list process inside Linux Bubblewrap and mounts exactly the caller-supplied --cwd and --folder directories at their canonical paths, or under a caller-chosen alias, exposing only controlled runtime and authentication/state paths and leaving other host paths absent. An explicit --home owns persistent agent configuration. It applies the web-search state to Codex and OpenCode through native controls, retains the agent's opaque native continuation during an interactive session, and mounts only what it was given. ALA leaves Pi unchanged and does not add a web-search extension. This generic runtime skill is not a task skill or a task-specific method.

Native permissions are the selected agent's rules for approving its own operations. ALA's ask-for-approval mode forwards Codex app-server or OpenCode server requests to a reply-capable host; full-access removes those native prompts without removing Bubblewrap. Pi supports full-access only. The host displays the native choices and returns an opaque option identifier, while ALA retains the exact native answer payload. No host approval cache replaces the backend's policy, and native remembered grants need not survive a recreated backend process.

Execution routing

Execution routing chooses between MainAgent model-backed execution for a general request and coding-agent execution when --ca/--agent is selected or a folder is supplied.

ALA forwards model, tag, and reasoning overrides to AchillesAgentLib for direct model work. Coding-agent backend and persisted native model selection remain independent from those overrides.

Agentic execution

Agentic execution is a bounded multi-step mode in which an eligible agent may plan, invoke tools, retry, validate, and synthesize a result. It is intended for work whose procedure cannot be completed adequately by one straightforward model call.

Retry limits and escalation policy must remain finite; ALA does not expose a separate command that directly selects this mode.

Task workspace

A task workspace is the directory tree a coding-agent execution can read and write. ALA binds the caller's explicit --cwd, or a retained temporary directory when it is omitted, read-write at its canonical path or under /workspace/<alias> inside Bubblewrap.

A task workspace is not an implicit copy of the caller's source repository and does not give ALA general ownership of that repository. Additional read-only or explicitly writable directories are supplied through --folder <path> [write] [as <alias>]. ALA mounts exactly what it is given and never discovers, creates, mounts or overlays task skills.

Code Skill

A Code Skill in this documentation refers to ALA's core runtime skill for authenticated coding-agent delegation. It is not a caller task skill.

ALA discovers the descriptor through its temporary registry and delegates execution to AchillesAgentLib. The component that distributes the skill remains responsible for its module, contract, and verification rules.

Soul Gateway

Soul Gateway is an AchillesAgentLib model provider that can resolve semantic model names such as plan, fast, write, and deep. An operator can configure external access with SOUL_GATEWAY_BASE_URL and SOUL_GATEWAY_API_KEY.

AchillesAgentLib loads an applicable .env file by walking upward from the current working directory and preserves environment values that are already set. The bundled model configuration maps the default planning model to soul_gateway/plan; deployments may replace that configuration through LLM_MODELS_CONFIG_PATH.

Ploinky

Ploinky is an external agent-hosting environment described by ALA's integration contract. A deployment may expose ALA operations through Ploinky interfaces or use a Ploinky agent as an executor when its advertised capabilities match the request.

ALA remains a standalone CLI and must not require Ploinky. Concrete hosting and remote-agent protocols remain integration contracts outside the implemented standalone runtime.

WebChat

WebChat is the Ploinky browser conversation interface through which a hosted ALA agent may receive task requests. It is an optional integration surface and does not replace the standalone ala command.

The ALA repository defines the shared request and result contract but does not own WebChat transport. Ploinky owns authentication, session transport, and browser hosting behavior.
