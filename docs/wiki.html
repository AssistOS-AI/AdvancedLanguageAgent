Advanced Language Agent Wiki

This page is the canonical reference for specialized project terminology. Each entry explains one concept and links only to different concepts needed to understand its relationships.

AchillesAgentLib

AchillesAgentLib is the external JavaScript library installed under the package identity ploinky-agent-lib. ALA uses it for MainAgent, LLMAgent, model tags, sessions, cancellation, and the internal Code Skill that bridges MainAgent to coding-agent execution. AchillesAgentLib does not discover task-repository SKILL.md files.

ALA resolves the library from an explicit path, the ACHILLES_AGENT_LIB_PATH environment value, a sibling checkout, or the package dependency. Model providers and concrete model identifiers remain AchillesAgentLib configuration. ALA passes supported overrides to the library and does not reimplement provider credentials or model invocation.

Task skill (SKILL.md)

A task skill is an Anthropic-style declaration defined in SKILL.md inside an independently versioned task repository. The repository owner defines the methodology, required checks, and acceptance conditions.

A task skill owns domain procedure and is selected by name through --skill or by a coding agent from the available catalog. Its frontmatter supplies a lowercase hyphenated name and a non-empty description. ALA mounts the skill directory and its relative resources in an isolated coding-agent workspace; it does not convert the descriptor into an AchillesAgentLib skill.

Task repository

A task repository is an independently installed and versioned directory that packages one coherent family of specialized work and its task skills, each declared in SKILL.md. Operators register persistent repositories from Git URLs with ala repo add or interactive /repo add, and may supply local repository paths through ALA_TASK_REPOSITORIES.

ALA recursively discovers Anthropic SKILL.md descriptors, validates their required frontmatter, combines canonical repository paths, and rejects duplicate skill names. It does not search task repositories for AchillesAgentLib descriptors. A Git URL passed to a persistent add command is cloned into the ALA data directory and represented in configuration by its managed local path. A registration can be removed by its Git repository name without .git, registered path, or original Git URL; duplicate short names require an exact path or URL. Interactive TAB completion suggests short names for /repo remove. Removing a registration changes only ALA's configuration and does not delete local files or managed clones. Interactive additions and removals refresh the catalog before the next prompt by changing the strict read-only task-skill mount set; workspace files, selected backend, native continuation, MainAgent conversation, and symbolic-detection state remain active. Task repositories are optional because general requests remain available with an empty catalog.

Skill catalog

The skill catalog is the set of enabled task skills that one ALA runtime discovers from persistent and environment-provided task repositories after canonical path deduplication and Anthropic manifest validation.

The catalog may be empty. In that state MainAgent performs general model-backed execution. When a catalog and coding agent are available, ALA mounts the skill directories under .agents/skills and asks the agent to select a matching descriptor; --skill selects one named entry before agent execution.

Discovery registry

The discovery registry is a process-scoped temporary directory created by ALA for AchillesAgentLib. It exposes only ALA-owned generic runtime skills, including the internal coding-agent bridge, to one MainAgent. Task-repository SKILL.md descriptors remain outside this registry.

ALA removes the registry when runtime creation fails or when execution closes. Anthropic task skills use separate strict read-only mounts inside the coding-agent task workspace, which keeps AchillesAgentLib discovery isolated from the task catalog.

MainAgent

MainAgent is the AchillesAgentLib coordinator that ALA creates for each runtime. It receives the discovery-registry path, prepares available skills, retains the active conversation, and executes prompts through its configured LLMAgent and supported skill subsystems.

MainAgent executes general requests and invokes ALA's internal coding-agent bridge. It does not discover Anthropic task skills; ALA selects or catalogs those descriptors before it calls the bridge. ALA forwards cancellation to MainAgent and shuts it down before removing the temporary registry.

LLMAgent

LLMAgent is the AchillesAgentLib class through which ALA's model-backed work runs. It resolves an explicit model, semantic tags, reasoning effort, and configured defaults into an eligible provider invocation.

ALA supplies command-line or environment overrides but does not call providers outside LLMAgent. If no model is explicitly selected, AchillesAgentLib applies its configured defaults, which may point to Soul Gateway or another provider.

Generic execution capability

A generic execution capability describes how ALA can run work without embedding a domain-specific method. The architecture recognizes direct, fast, and deep model execution, authenticated coding-agent execution, multi-step agentic execution, web and research access, and temporary workspace creation.

General requests may use direct model services, while Anthropic task skills always use a detected coding agent that can apply its own tools inside the temporary workspace. Availability depends on configured providers and installed executors; a named capability does not guarantee that every deployment supplies a matching backend.

Coding agent

A coding agent is a supported authenticated command-line agent that can plan, use tools, validate intermediate work, and return a final response for a bounded ALA request. The standalone runtime supports Codex, OpenCode, and Pi. Although these tools can edit code, ALA uses them as general executors for language, research, planning, verification, transformation, and bounded code-fragment tasks.

ALA detects their executables when each process starts and registers a generic Code Skill when at least one is available. The agent keeps ownership of its authentication, provider configuration, model catalog, and search-provider limits, while ALA may persist one user-selected native model identifier per backend and one shared Boolean web-search setting. ALA runs every backend and model-list process inside Linux Bubblewrap, mounts the task workspace read-write at /workspace, mounts discovered Anthropic skills strictly read-only, exposes only controlled runtime and authentication/state paths, and leaves other host paths absent. An explicit --home owns persistent agent configuration; an explicit --cwd owns persistent workspace data. It applies the web-search state to Codex and OpenCode through native controls, retains the agent's opaque native continuation during an interactive session, and removes only temporary workspaces it created. ALA leaves Pi unchanged and does not add a web-search extension. This generic runtime skill is not a task skill or a task-specific method.

Execution routing

Execution routing chooses between MainAgent model-backed execution for a general request and coding-agent execution for an Anthropic task skill or explicit --ca/--agent request. Task-skill execution must not change the selected descriptor's domain procedure.

ALA forwards model, tag, and reasoning overrides to AchillesAgentLib for direct model work. Coding-agent backend and persisted native model selection remain independent from those overrides.

Symbolic routing

Symbolic routing is an experimental instruction-only task-selection path enabled inside an interactive session with /symbolic detection on. It extracts actions, objects, targets, modifiers, structural markers, and relationships, then compares that evidence with optional routing metadata in task-skill declarations supplied by task repositories.

The router selects one skill before coding-agent execution only for deterministic or sufficiently strong high-confidence matches. Ambiguous and unknown requests use abstention and let the coding agent inspect the full catalog. /symbolic detection off disables the experimental path for the remainder of the session.

Abstention

Abstention is the symbolic router's decision not to force a task match when its instruction evidence is ambiguous or unknown. The coding agent receives the full catalog and may select a skill after reading its description, so symbolic uncertainty does not force an unrelated specialized method.

The routing design treats a false confident selection as more harmful than abstention. Concrete confidence thresholds remain deployment configuration and are not fixed by the current CLI.

Agentic execution

Agentic execution is a bounded multi-step mode in which an eligible agent may plan, invoke tools, retry, validate, and synthesize a result. It is intended for work whose procedure cannot be completed adequately by one straightforward model call.

A task skill continues to own the task procedure and acceptance conditions. Retry limits and escalation policy must remain finite; ALA does not expose a separate command that directly selects this mode.

Task workspace

A task workspace is an isolated temporary directory for one multi-stage request. It may contain explicit input, retrieved sources, intermediate artifacts, verification results, and final output needed by a task skill or agentic execution path.

A task workspace is not an implicit copy of the caller's source repository and does not give ALA general ownership of that repository. Coding-agent execution binds an explicit --cwd, or an ALA-created temporary directory, at /workspace inside Bubblewrap and mounts selected task-skill directories strictly read-only under /workspace/.agents/skills. The runtime removes only a temporary workspace it created; arbitrary extra host-folder mounts are unsupported.

Code Skill

A Code Skill in this documentation refers to ALA's core runtime skill for authenticated coding-agent delegation. It is not a task-skill and is not defined in a task repository.

ALA discovers the descriptor and delegates execution to AchillesAgentLib. The component that distributes the skill remains responsible for its module, contract, and verification rules. A generic core Code Skill does not become a task skill.

Soul Gateway

Soul Gateway is an AchillesAgentLib model provider that can resolve semantic model names such as plan, fast, write, and deepSOUL_GATEWAY_BASE_URL and SOUL_GATEWAY_API_KEY.

AchillesAgentLib loads an applicable .env file by walking upward from the current working directory and preserves environment values that are already set. The bundled model configuration maps the default planning model to soul_gateway/plan; deployments may replace that configuration through LLM_MODELS_CONFIG_PATH.

Ploinky

Ploinky is an external agent-hosting environment described by ALA's integration contract. A deployment may expose ALA operations through Ploinky interfaces or use a Ploinky agent as an executor when its advertised capabilities match the request.

ALA remains a standalone CLI and must not require Ploinky. Concrete hosting and remote-agent protocols remain integration contracts outside the implemented standalone runtime.

WebChat

WebChat is the Ploinky browser conversation interface through which a hosted ALA agent may receive task requests. It is an optional integration surface and does not replace the standalone ala command.

The ALA repository defines the shared request and result contract but does not own WebChat transport. Ploinky owns authentication, session transport, and browser hosting behavior.

Routing evaluation

Routing evaluation compares explicit Anthropic skill selection, coding-agent catalog selection, and experimental symbolic-first selection against one request corpus. It measures whether each path selects the expected method and ultimately produces the correct result.

The corpus includes canonical requests, paraphrases, multilingual input, spelling errors, ambiguity, multi-step work, missing parameters, and unsupported tasks. False confident symbolic selection receives a greater penalty than abstention because it bypasses the safe default path.
