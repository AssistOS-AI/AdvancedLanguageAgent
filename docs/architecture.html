Documentation / Architecture

Runtime architecture

ALA owns request loading, configuration, sandboxed coding-agent delegation, normalized output, and cleanup. It mounts exactly the directories the caller supplies through --cwd and --folder and never manages task skills.

System architecture

The CLI and input loader compose one request from command arguments and supported payload sources. Configuration establishes the current models, backend priority, and web-search state. The runtime passes the request through MainAgent, then either uses direct LLMAgent execution or the internal coding-agent Code Skill. CodingAgentService owns backend discovery, Bubblewrap construction, native CLI invocation, event parsing, and mount handling.

Responsibility boundary

The caller decides which directories are visible, which working directory is writable, and what task methodology to follow. ALA mounts those directories at their canonical paths, or under a caller-chosen alias, and delegates to an authenticated coding agent when one is selected.

ALA does not discover, copy, mount or overlay task skills. It validates the supplied directories, mounts each read-only unless marked write, and lets the selected backend work inside that layout. Direct provider authentication and installed coding-agent state remain owned by their respective runtimes; ALA exposes only controlled state paths inside the sandbox.

Process and workspace lifetime

Single-shot and interactive execution share the same components but have different lifetimes. A single-shot invocation creates one ALA runtime for one request. If the coding-agent route is selected, it uses an explicit --cwd or creates a retained temporary directory, mounts the caller folders, runs the selected backend, and returns the normalized result. A later invocation normally starts independently. Explicit session mode reloads the pinned backend and native continuation from the supplied home and requires the same cwd. Codex app-server and Pi RPC provide live steering; OpenCode executes queued follow-ups sequentially.

An interactive invocation retains one ALA runtime. Its working directory is created lazily and reused until the session exits; the first selected coding backend becomes pinned, and that backend's native continuation remains available to later prompts in the same interactive process. Model and web-search commands can update the retained runtime for subsequent turns. These interactive guarantees do not apply across separate one-shot processes.

Native permission decisions belong to the selected backend. ALA transports display choices and opaque replies through its event/control stream without storing an authorization cache. Codex uses app-server approval requests for controlled execution. OpenCode uses one authenticated loopback server per execution, preserving its saved native session while isolating transient permission grants. Pi has no native tool-approval prompts and rejects ask-for-approval. Control-channel loss cancels the owned operation; it does not grant access.

Repeatable --folder <path> [write] [as <alias>] options expose caller-owned directories. ALA handles path validation and mounting only. The caller owns dependencies, configuration, communication protocols, and cleanup. Unix sockets inside a mount remain caller-owned and accessible according to their permissions.

Discovery and portability

ALA's only discovery is the process-scoped registry that exposes the internal coding-agent Code Skill to MainAgent. It never scans a caller workspace for task descriptors.

AchillesAgentLib is installed through the ploinky-agent-lib dependency in package.json. A manual path, ACHILLES_AGENT_LIB_PATH, and a sibling checkout remain supported before package resolution. Imported task skill instructions, code, pages, and specifications remain in the repository that owns them.
